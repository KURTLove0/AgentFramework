## 创建、检查和恢复

在使用当前源码的 Python 环境中执行。先等待任务结束，建议停止本机服务后再备份。

```sh
# 保存完整的本机核心数据。文件名须尚不存在，上级目录须已存在。
python -m agent_framework --data-dir .agent-data backup agent-data-backup.zip

# 校验并查看工作空间、执行记录、对话和已保存草稿数量。
python -m agent_framework verify-backup agent-data-backup.zip

# 恢复到新的目录，保留现有目录。
python -m agent_framework restore-backup agent-data-backup.zip .agent-data-restored
```

成功时输出 JSON，包含 `valid: true`、备份时间、应用版本或恢复目录。失败返回退出码 1，并说明原因。再次备份请使用新文件名；再次恢复请使用新目录。

检查恢复结果后，用恢复目录和原来的租户、主体启动。例如，源码工作台通常使用以下参数：

```sh
python -m agent_framework --data-dir .agent-data-restored --tenant tenant-demo serve --principal demo-user --port 8787
```

使用安装脚本启动过的工作台，应继续使用原来的 `AGENT_TENANT` 与 `AGENT_PRINCIPAL`；安装脚本默认是 `local` 与 `local-user`。切换数据目录时先停止原服务，避免占用相同端口。

## 备份范围

范围是指定数据目录内**所有租户、工作空间和主体**的核心数据。两个数据库一起保存：

| 文件 | 内容 |
| --- | --- |
| `runtime.sqlite3` | 智能体与配置、知识/记忆/经验、Skills 与资源、工作空间、任务及对话、流程及排队请求、审计、授权、每日计划与评测 |
| `mock-business.sqlite3` | 模拟业务对象、已保存草稿、幂等记录与工具调用次数 |
| `manifest.json` | 格式版本、应用版本、备份时间、两个数据库的大小和 SHA-256 |

日志、测试子目录、导出文件以及数据目录外的 CLI 登录态不进入备份。浏览器保存的主题、画布位置、未提交到服务端的标签页编辑及待核对记录也不进入备份；服务端已保存的任务草稿和提交回执包含在数据库中。数据库中用户自行保存的正文与配置按原样保留。备份文件权限为仅当前用户可读写；恢复目录和文件也采用仅当前用户可访问的权限。

这是拥有本机数据目录访问权的维护者运行的命令。全库备份不经由普通工作台页面提供下载，网页现有的租户、空间与主体访问范围继续适用。

## 一致性与校验

创建备份时，先同时取得两个数据库的写入保留锁，再用 SQLite 备份接口复制数据库；已提交但仍在 WAL 日志中的记录会纳入快照。复制期间两个库保持同一组已保存事实。随后检查数据库完整性、核心数据结构和打包后的校验和，完成后才发布备份文件。

有效任务租约、工作流租约或每日派发租约存在时，会要求等待；数据库正在写入时有限等待后报错，可通过 `backup --timeout 5` 调整每次取得写锁的等待秒数，最大 30 秒。服务空闲时允许备份，推荐在停止服务后执行。

读取备份时检查文件名单、重复成员、文件类型、大小、格式版本、应用版本、SHA-256 与数据库完整性。单个数据库上限为 512 MiB。当前支持 ZIP 中两个数据库和一份清单；新版应用创建的备份要求先升级应用再恢复。校验和用于检查文件损坏，恢复时也检查已知的数据库结构。

## 恢复与中断保护

- 完整验证结束后才创建目标目录；已存在的文件、目录或符号链接都会拒绝覆盖。备份文件发布时也使用排他创建，避免并发操作覆盖同名文件。
- 恢复保留任务身份、冻结快照、具体授权及其原有效期、对话、排队意图和业务幂等事实。旧进程持有者和租约会清理，任务的租约代数递增；不会把旧进程当作恢复目录的活跃执行器。
- 恢复成功后写入 `restore-receipt.json`，记录源备份时间、源版本、恢复时间及清理的租约数量。
- 普通写入失败会在路径保护仍有效时清理本次创建的文件，并在清理同步后撤去保护；清理失败或有其他进程留下的文件时保留保护。创建目标目录前先持久保存路径保护标记，目录中另保存 `.restore-in-progress`。进程被强制终止时，执行器会拒绝启动未完成恢复的路径，包括尚未创建目标目录的中断窗口。完整数据库与目录项确认同步后，收尾异常不会再删除已经恢复的数据。
- 中断后仍可使用原备份恢复到另一个新目录，原工作台和原备份继续保留。恢复命令本身不启动任务或模型；启动服务后，已保存的排队请求沿用正常调度与权限检查。

## 验证

```sh
python -m unittest tests.test_backups -v
python -m unittest discover -s tests -q
```

16 项专项回归覆盖全表内容往返、多空间/租户恢复、WAL 中的记录、三种活跃租约、写锁拥堵、旧租约清理、损坏和不兼容备份、已有目标与并发发布、恢复写入失败、进程强制退出后的启动阻止、工作线程初始化繁忙后的释放与重试，以及命令行实际调用。路径样本包含中文和空格。

恢复实验包含两条执行路径：排队流程使用原快照完成，模拟草稿创建一次；写入后中断的任务恢复后先核对已有草稿，创建调用仍为一次。测试仅使用临时数据目录，没有对日常工作台执行备份、覆盖或迁移。

本轮完整回归 407 项通过；16 项专项在将数据库资源泄漏警告作为错误的模式下通过。另从干净源码快照构建独立 wheel，在源码目录外直接从包内执行创建数据库、备份、校验、恢复和恢复后启动检查，均通过；成功恢复后无未完成标记残留。此验证未覆盖或重新发布现有发行包。
