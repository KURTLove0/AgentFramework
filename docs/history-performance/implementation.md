# 任务历史读取与稳定分页

2026-10-31 的界面改进见 [运行历史的搜索、翻页与读取恢复](../reliability/run-history-recovery.md)：主动查询不等待整页刷新，失败可重试原页或恢复上次成功的完整条件。下文保留本轮后端查询与游标改进的历史验证记录。

2026-10-29。本轮改进历史任务较多时的列表读取、后台检查和分页，并修复连续对话中一次刷新与实时推送的竞态。改动位于当前源码。

## 列表读取

此前列表会先读取租户内的完整运行状态，再为每个对话调用完整详情；每一轮都读取正文、动作、验收和审计记录。即使界面只显示一页标题，后台也会反复加载这些历史内容。

现在先在数据库中过滤工作空间、主体和根任务，读取标题所需的字段，再分批汇总各轮状态、更新时间、截止时间与用量。读取依据仍是原始运行与对话记录，没有另设需要同步的状态缓存。完整正文和审计继续在详情、导出和模型上下文中按原有规则使用。

工作台待办使用同样的摘要，并批量检查最新轮次租约。每日计划配置未变化且已有冻结计划时直接返回原计划；需要生成或检查重复目标时也使用摘要。对话后台检查会跳过已完成的历史线程，恢复当前轮次时先检查轻量状态，避免逐轮加载已完成结果。

## 实测

在同一台本机、同一份隔离数据上读取 50 条列表：120 个任务，每任务 3 轮，每轮 4 KiB 正文及 3 条约 4 KiB 审计记录，无真实模型调用。

| 指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 单次读取耗时 | 1.4861 秒 | 首次复测 0.0184 秒 |
| SELECT 查询数 | 2881 | 2 |
| 审计读取次数 | 360 | 0 |
| 动作读取次数 | 480 | 0 |
| 返回 / 总任务数 | 50 / 120 | 50 / 120 |

最终重复三次测量为 0.016745、0.016121、0.015389 秒，中位数 0.016121 秒；每次均为 2 次 SELECT，未读取审计或动作。这些是开启查询追踪后的本地接口测量，不包含浏览器绘制、网络或模型耗时，不作为其他机器上的固定性能承诺。

可运行以下命令生成独立临时数据并重新测量，结束后自动清理：

```sh
.venv/bin/python scripts/benchmark_history.py
.venv/bin/python scripts/benchmark_history.py --tasks 500 --turns 3 --repeats 3
```

## 分页与筛选

新游标保存排序时间和任务 ID，同时记录当前租户、空间、主体、排序与筛选条件的摘要。列表中的游标任务收到补充回答、更新时间变化后，下一页仍按原排序边界继续；切换筛选或排序后使用旧游标，会要求返回第一页。同一时间戳通过任务 ID 确定顺序。

旧版仅包含任务 ID 的游标继续按当前可访问结果解析。列表按实时状态更新，任务总数仍可随执行和新增记录变化；返回第一页可读取最新结果。日期范围、排序和页大小在读取历史前校验，非有限日期会明确报错。

## 状态一致性与隔离

- 列表汇总结果与完整对话逐项比对，覆盖已完成、等待输入、等待授权、排队、取消排队和失败轮次，以及最新轮次的模型用量和执行状态。
- 工作空间、主体和租户在数据库查询中筛选。已登记为私有对话的旧任务，也从其他主体的列表中排除。
- 分批查询限制绑定参数数量；专项用例跨越 400 条边界，并完整遍历 413 个任务，核对无丢失或重复。
- 取消排队会更新对话活动时间，即使没有新的模型事件，列表也能反映此次操作。

浏览器回归还发现：轮询可能先更新页面内存，实时推送再收到相同结构时误以为界面已更新，导致“已取消排队”等状态暂时未画出来。现按对话版本判断新旧，并核对实际渲染的结构。旧响应不能覆盖较新操作；推送即使与内存状态相同，也能修复落后的画面。生成中的文本仍沿用局部更新，保留输入和滚动体验。

本轮完整回归 424 项后端测试通过、57 项前端测试通过，三组浏览器验证通过。更新时间升序和降序的游标边界更新均通过专项复测；代码编译和补丁空白检查通过。
