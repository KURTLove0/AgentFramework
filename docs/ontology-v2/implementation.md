# 岗位评测契约与业务 Ontology 优化

2026-10-23，源码更新。岗位评测和本体编辑、生成、发布、检索、导出均已接通。现有安装包保留原版本，使用本轮源码需重启本地服务。

## 参考依据与落地选择

参考资料均为官方文档，查阅日期为 2026-10-23：

- [Palantir Ontology 概览](https://www.palantir.com/docs/foundry/ontology/overview)：采用对象、属性、关系与动作的建模思路，将既有概念层扩展为可浏览、可校验的业务对象模型。
- [Palantir 对象类型](https://www.palantir.com/docs/foundry/object-link-types/object-types-overview) 与 [关系类型](https://www.palantir.com/docs/foundry/object-link-types/link-types-overview)：明确类型和实例的区别，并在关系类型上声明端点类型和数量约束。
- [W3C SHACL](https://www.w3.org/TR/shacl/)：使用形状描述约束，输出带焦点节点、属性路径和约束原因的报告；将支持的约束导出为 SHACL 词汇，交由独立验证器复核。
- [W3C SKOS](https://www.w3.org/TR/skos-reference/) 与 [PROV-O](https://www.w3.org/TR/prov-o/)：保留概念、标签及上下位/关联语义，用来源关系记录类型、对象和关系断言的依据。

以上模式结合本项目的冻结岗位、资料审核、任务授权与独立验收实现。本轮增加的是受控的语义和业务模型层，使用现有 SQLite 与执行网关。完整 OWL 推理、通用 SHACL/SPARQL 执行、外部图数据库及 Palantir 服务连接尚未提供。

## 基于岗位的评测

打开“岗位评测”，选择 Agent 后点击“岗位评测契约”：

1. 核对岗位角色与归属团队，设置岗位分数阈值；留空时跟随空间规则。
2. 配置身份、职责、标准、交付四项维度的分值，须为正整数、合计 100。默认仍为 10 / 35 / 35 / 20。
3. 为每项职责和每个已登记标准设置权重及最低达成分数。
4. 保存会创建新的 Agent 配置版本。新任务冻结完整契约；每日模板需要重新选择 Agent 版本。已提交任务和历史报告继续使用各自原版本。

评测契约 `job-contract@1.0.0` 由实际岗位定义编译，包含身份、领域、允许能力、职责/交付物/验收映射、标准检查映射、权重与阈值，随编译岗位一并计算内容哈希。评分规则版本为 `job-history@2.0.0`。

| 项目 | 当前评测依据 |
| --- | --- |
| 身份与边界 | 任务与岗位引用和版本一致；名称、角色、团队一致；任务领域一致；快照、编译岗位和契约哈希有效；实际工具引用属于岗位能力 |
| 职责履行 | 每项职责映射的验收通过率，核对对应报告/草稿的实际存在与产物哈希，再按职责权重汇总 |
| 标准达成 | 每项冻结标准对应的验收通过率，按标准权重汇总 |
| 任务交付 | 是否到达成功终态 |
| 证据完整性 | 检查持久化证据的数据哈希、运行 ID 与租户范围；证据缺失或被改动时，验收不得计为通过 |

各项达成率为 0–100 分。角色文字通过岗位的领域、能力边界、交付物和检查映射落实为可测条件；本轮评测不额外推断自由文本角色的人格或风格。

有效总分阈值取岗位与空间要求中较严格者。必选验收失败、职责/标准低于本项要求、身份或边界检查失败、交付物缺失、未完成交付均会提醒，不能通过提高其他项权重绕过。等待授权/材料的运行暂不评分；人工取消不计分。

报告显示逐项达成分数、最低要求、权重、产物和来源引用。旧任务缺少评测契约时，仅从其原冻结岗位派生，报告标注来源；不会读取当前编辑后的 Agent 代替历史岗位。旧报告保留，手动补评形成新规则版本的报告。相同输入仍采用内容指纹去重，提醒确认仅记录已阅。

## 业务本体的生成与编辑

在“知识库 → 本体 Ontology”中点击“生成本体”，选择 Agent 与 1–12 份有效、已发布的资料。“同时抽取业务对象与约束”默认开启：

- 概念层继续保留名称、定义、别名、属性及关系。
- 业务模型增加对象类型、对象实例、关系类型、实例关系与登记能力映射。
- Agent 仅应从来源明确的业务标识与属性事实建立实例。离线生成保留空实例集，可在编辑器中补充；没有根据共现自动制造业务关系。
- 离线生成遇到同名资料时保留各自的概念、事实和来源，使用来源版本引用区分名称；不会仅凭标题相同合并业务含义。
- 真实模型输出使用封闭 Schema，所有来源引用被限定为所选资料。实例属性以结构化条目输出，后端检查重复属性后转换为供编辑器使用的属性映射。布尔值与有限数值按真实类型校验。

已有概念本体可通过“启用业务对象建模”扩展。旧资产无需修改或迁移即可继续使用。

对象类型声明对应概念、主键与属性。属性可配置 string / number / boolean / date、最少/最多值数、枚举及数值范围。主键须为必填、单值文本或数值；同类型内唯一，数值 1 与 1.0 视为同一键。属性改名会同步实例中的属性键，避免丢值。

关系类型声明两端对象类型及一对一、一对多、多对一或多对多约束；实例关系据此检查端点存在性、类型、重复及数量。多值属性不允许重复值。实例中未定义的属性、错误类型、非法日期、越界值、非法枚举和缺少必填项都会形成可定位报告。

“校验模型与实例”展示全部违反项，包括对象标识、属性路径、约束与原因。校验期间编辑内容会使回执失效，需重新校验。保存、沉淀及发布也执行同样的约束检查；检查失败时不会发布。概念别名不得与首选标签相同或在同概念内重复；上下位关系与组成关系分别禁止循环。

模型上限为 16 个对象类型、每类型 24 项属性、32 个关系类型、200 个对象、400 条实例关系、32 项动作映射；单个模型最多 200 KB，整份生成提案仍受 256 KB 限制。

## 对象浏览、动作映射与检索

保存本体为草稿后，依次提交审核、发布。点击“浏览业务对象”可按类型和属性搜索实例，查看属性、关系和来源。

动作映射仅能引用已登记能力。选择一个 Agent 后可“核对”该岗位是否拥有映射能力，并显示 READ/WRITE 效果及任务授权要求。核对只返回映射与参数 Schema，不创建任务或调用业务工具；实际执行仍使用原任务入口的范围、预算、授权、网关和独立验收。

概念检索默认沿两跳关系扩展，可设 0–3 跳并限制关系类型。直接命中排在路径命中之前，每跳衰减 0.6；返回路径方向、得分及每一跳的来源。检索上限保持有界，不把路径存在当作新的业务事实。知识检索继续回到这些已授权来源，供原引用与验收机制核对。

概念名称和别名先做去除首尾空白、忽略大小写的精确匹配，再参与分词匹配，因此 `R`、`A`、`C++`、`C#` 等短标签也可用于检索。非空查询即使未产生分词，也不会被当成无筛选查询而返回全部知识。

本体冻结所选资料的版本引用和哈希。资料发布新版本后，仍有效的旧版本继续作为已有本体的依据；本体命中的知识检索严格返回其引用版本，不会用新版本替换。普通知识检索仍默认选择最新有效的已发布版本。需要采用新资料事实时，应选择新版本重新生成和审核本体。

本体和所引用资料均需当前有效、已发布、哈希一致且对当前主体可访问。有效期包含开始时刻，不包含结束时刻。来源撤回、过期、内容哈希变化或不再可访问时，本体停止参与检索和对象查询；本体自身尚未生效或过期时，概念检索、对象查询和动作映射核对也停止使用它。资产校验接口会报告本体有效期问题，历史版本、审计及 JSON-LD 导出继续可读。租户、工作空间、项目、环境、主体隔离沿用现有规则。

上述边界与完整 HTTP 编写流程的回归见 `tests/test_ontology_regressions.py`：覆盖生成、编辑、幂等沉淀、审核发布、修订、固定来源检索、知识问答引用、对象查询、动作核对、导出及失效阻断。

## 标准导出与版本

### 1.3.0 的生效版本、修复与原文核对

发布本体会记录当前生效版本。撤回新版后，旧版不会自动恢复参与检索；可在仍有效且来源可访问的已发布旧版上点击“启用此版本”。启用请求带当前生效版本引用，其他页面已改变生效版本时会拒绝覆盖。历史发布事件可用于兼容没有生效版本记录的旧数据。

过期、尚未生效、来源失效及未启用的版本在列表中直接显示原因；业务对象浏览只对当前可用版本显示。失败的生成记录如果保留了可编辑结构，可创建修复草稿。修复不会重新调用模型，原失败记录保留；重复请求复用同一草稿，约束未修正时不能沉淀。

“断言证据”支持概念、概念属性、关系、对象类型、属性约束、实例及动作映射。片段必须逐字出现于该断言引用的冻结来源中；保存来源哈希、Unicode 字符位置（从 0 开始，结束位置不包含在内）、人工核对状态与证据版本。换版本后需重新核对，旧记录保留。每个本体版本最多 256 条证据，每段最多 2000 字。人工核对表示已检查片段与断言的对应关系，系统不会自动据此证明业务事实正确。

新增接口：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/learning-proposals/{id}/repair` | `{revision}`，幂等建立修复草稿 |
| POST | `/api/ontologies/{ref}/activate` | `{expected_active_ref}`，明确启用所选版本 |
| GET / POST | `/api/ontologies/{ref}/evidence` | 读取断言与原文，或保存 `{path, source_ref, quote, reviewed, revision}` |

证据随 JSON-LD 导出，包含原文、来源和核对状态。对象实例仍使用有界快照；当前 200 个实例上限不变。检索会先选择有权限的候选资产，再解码和校验其版本；本体扫描按种类过滤，资产与发布事件增加范围索引。可用 `PYTHONPATH=. python scripts/benchmark_retrieval.py` 在临时合成数据上测量查询性能；该结果不能替代持续并发压测。

JSON-LD 导出包含：

- SKOS 概念、概念方案、标签、定义、别名、上位与关联关系。
- OWL 类、对象属性与 RDF 属性声明，用于业务类型及关系描述。
- SHACL NodeShape、属性类型、数量、枚举、数值范围、闭合属性集合、关系端点类型及正向/反向数量约束。
- PROV 来源引用；实例关系用 RDF Statement 保留断言来源。

IRI 使用资产标识和本地类型/对象标识组成稳定名称，修订通过 `owl:versionInfo` 与原资产版本记录表达。早先已导出的文件保持原样。数值以正确的十进制词法形式编码，支持科学计数法 JSON 数字的标准往返。

主键唯一与来源有效性属于应用层校验；通用 SHACL Core 验证器不会因此自动具备这些业务规则。工作台实现并导出上述明确子集，未宣称支持任意外部 SHACL 文档执行。

可在独立测试环境使用 [RDFLib/pySHACL](https://github.com/RDFLib/pySHACL) 复核：

```sh
python -m pip install rdflib==7.6.0 pyshacl==0.40.1
python scripts/verify_ontology_export.py docs/ontology-v2/example.jsonld
```

这是可选的开发验证依赖；工作台运行不依赖上述包。

## 接口与代码

所有写接口继续要求同源 JSON 和页面会话令牌；配置保存检查 Agent revision。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET / POST | `/api/agents/{id}/evaluation-contract` | 读取岗位契约 / 保存 `{revision, config}` 并产生 Agent 新版本 |
| POST | `/api/learning-proposals` | 本体生成可传 `operational: true` |
| POST | `/api/ontology-validate` | 校验 `{content, source_refs}`，返回结构化报告 |
| GET | `/api/ontologies/{ref}/validate` | 检查资产模型与来源当前状态 |
| GET | `/api/ontologies/{ref}/objects` | `query`、`type_id`、`limit` 筛选当前有效对象集 |
| POST | `/api/ontologies/{ref}/action-preview` | `{action_id, object_id, agent_id, agent_revision}`，仅核对映射 |
| GET | `/api/ontology-search` | `query`、`max_hops`、可重复 `predicate`，返回概念和来源路径 |
| GET | `/api/ontologies/{ref}/export` | 导出带 Shapes 与来源的 JSON-LD |

主要实现为 `evaluation_contract.py`、`agent_evaluation.py`、`ontology.py`、`ontology_model.py`、`webui/operations.js` 与 `webui/ontology_model.js`。本轮没有修改历史任务、自动授予能力或连接真实业务平台。
