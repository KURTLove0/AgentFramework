# 每日任务的持久派发与恢复

2026-10-31 新增工作台完整待办与计划直达链接：历史失败计划可从待办定位，超过近期概览范围的计划可独立读取。详见 [工作台完整待办与每日计划定位](../reliability/attention-inbox.md)。

2026-10-29。当前源码改进，每日计划继续使用原来的任务入口、固定 Agent 版本、预算、授权和业务幂等规则。

## 解决的问题

实测确认了两个旧行为：

- 在任务提交成功、运行标识尚未关联到计划时中断，修改模板后可覆盖原预览。重试会把旧目标的任务关联到新目标的条目，界面与实际执行不一致。
- 执行队列满时返回 429，已创建的自动启动任务依赖当天、仍启用且版本未变的定时检查。跨日或关闭定时后可能一直保持 `CREATED`。

现在先在数据库事务内确认空间、计划版本并保存派发请求，再提交每项任务。请求与计划目标绑定，排队不再被当作派发失败。每项任务仍使用由租户、空间、主体、计划及条目确定的稳定运行标识。

## 使用与状态

“生成今日计划”仍只创建预览。“派发今日任务”保存派发请求：

| 情况 | 行为 |
| --- | --- |
| 任务队列繁忙 | 所有可执行条目先关联原任务，保存自动启动请求，页面显示排队，无需重复点击 |
| 服务中断或重启 | 认领租约到期后，继续原计划与任务，不重新生成目标 |
| 已接受的请求跨日、修改配置或关闭定时 | 继续处理原请求；新设置只用于后续计划 |
| 等待授权、等待材料或任务进入终态 | 停止自动启动处理，保留任务原状态 |
| 意外派发错误、检查到工作进程已中断 | 保存错误并暂停后台重试；用户可检查任务后“重试原计划” |
| 已提交过任务的计划 | 保留原目标与固定版本，不能用新模板覆盖 |
| 尚未派发的预览 | 修改设置后仍可重新生成；全部条目受阻且未创建任务的计划也可以重新生成 |

关闭定时不会取消已经接受的请求。需要停止已创建的执行时，进入任务详情取消；取消状态会使对应自动启动请求结束。不会重放停机期间所有遗漏日期的新计划，仍只为当前时区的当日生成新计划。

Agent 在派发前变更或归档时，未创建的条目继续遵守原版本检查并显示受阻，不会偷偷采用最新版。已创建任务始终使用冻结快照。恢复和重试不重置预算、延长期限或续签原授权。

界面保留跨日、旧配置下的失败计划重试入口；较早的待处理和失败计划不会被最近 60 份记录的展示窗口隐藏。工作台待办也包含派发失败的计划。读取乱序和派发前发起的旧读取不能覆盖成功回执；回执后的页面刷新失败会明确说明操作已完成。

## 持久化与并发

无需新表。在 `workspace_daily_plans.data` 中增加兼容字段 `dispatch`：

```json
{
  "state": "PENDING",
  "requested_at": 1793260800
}
```

`PENDING` 表示派发或自动启动仍待处理；`COMPLETE` 表示条目已核对、无须继续自动启动；`FAILED` 表示需人工检查后显式重试。失败时增加 `failed_at` 与 `last_error`，最近一次错误在成功重试后继续保留，当前 `plan.error` 则清除。

计划认领仍使用现有数据库租约。版本检查和请求保存位于同一写事务中，重新生成预览也在事务内再次检查冻结状态。兼容没有 `dispatch` 字段的历史记录：生成前检查稳定运行标识，已经提交但尚未关联的旧任务也会使原计划保持冻结。找回任务时核对项目、主体、目标、Agent 固定版本、执行方式和业务对象；不匹配会阻止自动关联。

后台定时检查首先恢复所有已保存的 `PENDING` 请求，再按设置考虑今日新计划。恢复查询不依赖历史列表的展示窗口。未运行的派发请求即使尚无任务记录，也会阻止删除空间；备份、校验及恢复直接保留这些请求。

现有派发接口不变：`POST /api/daily-plans/{id}/dispatch`，仍提交 `{}`。容量不足时返回 200 和带 `status: "QUEUED"`、`dispatch.state: "PENDING"` 的计划，表示请求已保存；意外错误保留错误响应和可查询的失败状态。
