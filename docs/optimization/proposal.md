# Agent 框架优化方案

日期：2026-10-22。后续 P0/P1 实施与实际证据见 [助理框架实施与验收](../assistant/implementation.md)。适用范围：当前 AgentFramework 仓库，延续原有“以人建模”的技术方案，面向下一轮工程改造。

建议保留现有可恢复执行内核，优先补齐 **Agent 定义编译、知识与记忆治理、统一动作效果契约**。这样，身份和职责决定工作边界，知识与经验提供依据，模型负责理解和提案，确定性运行时负责执行事实、授权与完成判定。

首期交付仍以“变更评估并创建草稿”为样板。新增业务场景通过领域包扩展；多 Agent 协作、分布式调度和自动经验发布放在后续阶段。本次交付包括优化设计、目标架构图和可运行的契约检查样例，生产运行时改造按本文路线实施。

## 一 拟人模型对应的工程对象

“人—大脑—手脚”的骨架可以保留，同时增加目标、环境反馈和学习治理。Agent 是持续存在的执行主体；每次任务产生独立运行，模型是可替换的认知组件。

| 人的概念 | 工程对象 | 应承担的责任 |
| --- | --- | --- |
| 身份与岗位 | AgentDefinition | 名称、角色、归属、职责、适用领域、交付物 |
| 工作任务 | TaskContract | 本次目标、资源范围、执行主体、验收、预算、期限 |
| 知识 | KnowledgeAsset | 有来源、版本、时效和访问范围的事实与规则 |
| 当前记忆 | WorkingMemory | 当前计划、证据、未决动作和检查点；以持久化事实恢复 |
| 过去的经历 | EpisodicMemory | 某次运行发生了什么，链接到原始证据和结果 |
| 经验 | ExperienceRule | 在什么条件下采用什么方法，支持证据和反例是什么 |
| 工作方法 | SkillDefinition | 可复用步骤、依赖能力、输入输出、适用条件与评测 |
| 可用本领 | CapabilityDefinition | 具体动作的输入输出、效果、范围、恢复与验证契约 |
| 思考与决策 | CognitiveRuntime | 组织上下文、规划、提案、解释证据缺口、有限修正 |
| 感官与手脚 | ActionGateway 与 Adapters | 受控读取、执行、回读和结果归一化 |
| 纪律与考核 | PolicyEngine 与 Verifier | 当前是否有权执行，实际结果是否满足标准 |

关系调整为两个闭环：

```text
岗位定义与任务契约
          ↓ 约束
知识 / 情节记忆 / 已发布经验 → 上下文编译 → 认知规划
                                  ↑             ↓ 结构化动作提案
                          工作记忆与证据 ← 独立验收 ← 网关执行 → 环境
                                  ↓
                            经验候选 → 评测 → 审核发布
```

运行反馈立即进入工作记忆。经验审核异步进行，不阻塞当前任务，也不自动改写权限和业务标准。交互目标架构见 [architecture.html](architecture.html)。

## 二 当前代码与目标的差距

原方案已提出知识、记忆、经验、能力分治。当前需要推进的是这些设计与已实现执行链之间的连接。

| 领域 | 当前代码事实 | 下一步改造 |
| --- | --- | --- |
| Agent 定义 | `agents.py` 保存名称、描述、Prompt、Skill、MCP；`runtime.registry_snapshot` 主要替换内置 Agent 的名称与引用 | 合并为一套可编译的岗位定义，结构化配置身份、职责、标准、知识空间和能力绑定 |
| 角色与权限 | `AgentSpec` 仍要求固定四个业务工具；角色文字没有独立授权语义 | 能力集由领域包和注册表解析；当前主体、资源和授权仍在执行时判断 |
| 知识 | 规范主要来自内置资源和模拟 `standards.read` | 增加可追溯知识资产、范围过滤、有效期、冲突处理和上下文清单 |
| 工作记忆 | `Store` 已保存运行、动作、事件、证据、验证、租约和检查点 | 保留为运行事实来源；新增摘要只供检索，不覆盖动作事实 |
| 长期记忆与经验 | `experience_candidates` 仅有待审核候选，没有评测、发布和检索闭环 | 建立情节记忆、经验候选、评测记录和发布版本 |
| Skill | 自定义 Skill 是内联方法说明；内置 Skill 另有结构化 manifest | 统一为版本化方法包，声明能力依赖、产物和验证器 |
| 动作 | 业务四工具走 Gateway；原生 MCP 在 LLM transport 内调用，只校验服务/工具白名单 | 所有调用登记效果契约；有副作用的 MCP/CLI 统一进入网关；原生读取通过受控代理记录 |
| 验收与恢复 | 参数哈希、幂等、意图持久化、外部回读和失效 worker 防护已实现 | 抽出领域验证器接口，保持已有恢复次序及幂等身份 |
| 场景扩展 | `contracts.py`、`gateway.py`、`planner.py`、`verifier.py` 绑定变更报告场景 | 提取 DomainPack，先完成现有场景的等价迁移，再接第二种任务 |

源文件：[Agent 配置](../../agent_framework/agents.py)、[契约](../../agent_framework/contracts.py)、[运行时](../../agent_framework/runtime.py)、[网关](../../agent_framework/gateway.py)、[存储](../../agent_framework/store.py)、[认知上下文](../../agent_framework/llm.py)、[验收](../../agent_framework/verifier.py)。

## 三 岗位定义与运行实例分开

### AgentDefinition 描述稳定岗位

建议包含：`identity`、`responsibilities`、`standard_refs`、`knowledge_spaces`、`skill_refs`、`capability_refs`、`policy_ref`、`runtime_profile_ref`、`prompt_template_ref`。

身份中的角色、归属和职责可供上下文编译、任务匹配与审计使用；真正的身份认证和授权使用服务端得到的 `principal` 与委托关系。本机 Codex 登录态只解决模型服务访问，不能成为业务系统授权凭据。

职责需要有交付物和验收映射，例如“评估变更风险”映射为评估报告及证据检查，“创建草稿”映射为授权写入及独立回读。“标准”分别绑定说明性文档和可执行验证器；只有文字、尚无验证器的标准不能直接成为自动完成条件。

### 编译为不可变快照

增加 `AgentCompiler`：

1. 解析领域包、Agent、Skill、能力、Schema、标准与验证器的具体版本。
2. 检查引用完整、依赖无环、方法所需能力属于岗位声明范围。
3. 确认工具效果分类、资源解析器、写入幂等与核对方式。
4. 冻结 Prompt 模板、模型配置、能力及适配器版本、标准和验证器摘要。
5. 输出 `CompiledAgent`，供任务提交时绑定。

编译输出表示“此岗位最多可申请哪些能力”。实际可执行范围在每次调用前取交集：

```text
岗位声明 ∩ 领域允许集 ∩ 当前组织策略 ∩ 当前主体授权 ∩ 本次任务资源范围
```

已有任务恢复使用原定义、方法和模型快照；当前授权、知识撤回限制及紧急禁用策略仍实时生效。冻结配置不冻结永久访问权。原始证据若因合规删除而不可再用，应明确暂停或转人工处理，不能自动用最新资料替换历史证据。

### DomainPack 承载业务差异

首个 `change-assessment@2` 领域包集中声明任务输入、领域约束、Skill、能力、产物 Schema、上下文供应器和验收器。运行内核只处理状态、授权、预算、分发、恢复与验收调度。

先把现有四工具和三项验收包装成等价领域包。验证结果一致后，再增加第二个只读场景，例如“知识问题答复并引用来源”，检验框架是否已摆脱报告字段硬编码。验证器通过受信注册表提供，模型不能提交可执行代码。

## 四 知识 记忆 经验与能力分别治理

### 资产类型和生命周期

| 对象 | 内容与生命周期 | 使用约束 |
| --- | --- | --- |
| 知识 | 草稿 → 审核 → 发布 → 过期或撤回 | 记录来源、版本、有效期、适用范围与替代关系 |
| 工作记忆 | 运行开始 → 每次检查点 → 终态归档 | 动作状态与未决写入精确保存，不由模型摘要重建 |
| 情节记忆 | 已发生事件 → 脱敏归档 → 保留或删除 | 保存运行/证据引用；“发生过”不代表“今后应这样做” |
| 经验 | 候选 → 离线评测 → 审核发布 → 废弃或撤回 | 带适用条件、支持案例、反例、指标与版本 |
| 能力与 Skill | 开发 → 测试 → 发布 → 退役 | 注册依赖、效果、验证与评测；描述可检索，执行依赖正式绑定 |

通用元数据至少包括 `tenant_id`、项目/环境范围、资产种类、来源 URI、来源版本、内容摘要、观察时间、有效期、访问策略引用、敏感级别、状态及 `supersedes`。来源权威性由治理配置决定，模型评分仅能辅助排序。

共享业务知识按租户/项目发布；主体偏好按用户或显式共享范围保存；岗位方法按已发布版本共享。不能因为两个任务使用同一 Agent，就共享不同用户的私有记忆。

### 上下文编译流程

```text
服务端身份与任务范围
→ 数据源访问检查及范围过滤
→ 检索候选
→ 时效、来源、版本与冲突检查
→ 内容去重与任务相关排序
→ 按信息预算组装
→ 生成 ContextManifest 并保存内容引用
```

访问过滤应在检索前实施，返回候选后再次校验，缓存键包含租户、主体/授权范围、项目、环境、查询和版本。向量索引只能协助找候选，不承担授权判断。

首期可用当前 SQLite 元数据与 FTS5 做文档/方法检索；本机 SQLite 已验证可使用 FTS5。中文检索需明确分词策略，先用领域关键词和确定性检索测试基线，再依据漏召回样例决定是否引入向量检索和重排。产品选型留在效果验证之后。

上下文按以下顺序保留：执行约束与验收、岗位与任务、精确未决状态、必需证据、适用知识、可选经验。摘要和低优先级内容先裁减；必需证据不足时请求补充，不通过删减安全约束满足 token 预算。

`ContextManifest` 记录资产/证据引用、版本、摘要、选用原因、排除原因和预算。当前 `_context` 同时传工作观察与证据集合，适合优先做重复内容去除和分阶段最小上下文；改造时需保证报告编写阶段仍拿到完整关键事实，创建阶段仍使用原样已验证报告。成本收益需实测，不能从去重设计直接推断降幅。

### 冲突 时效与记忆更新

实时业务事实以所属系统的权威读回为准；规范使用适用版本及生效期；同级来源冲突保留双方并标记待裁决。历史经验不能覆盖当前事实或强制标准。

任务执行中出现新观察时追加证据，不覆盖旧版本。影响写入前置条件的来源变化应使原提案失效并重新评估，沿用现有条件写机制。非关键背景知识过期可以排除；关键标准缺失或撤回时停止生成“已通过”结论。

### 经验晋升

从终态运行生成候选，至少记录：问题类型、上下文条件、采取的方法、原始证据、结果、失败/反例和局限。由离线回放验证适用性，再由指定审核角色发布新经验版本。

回放默认使用冻结证据和模拟适配器，不重复执行真实写操作。新增模型推理计作独立评测运行。经验不能自行扩大能力、降低验收或发布新的执行策略；要改变这些内容，应走相应配置的测试与发布流程。

## 五 Skill Tool MCP 与 CLI 的关系

Skill 组织工作方法；Capability 给出动作语义与效果契约；Tool 提供可调用操作；MCP、CLI、SDK/HTTP 适配器完成协议转换。同一个“读取变更”能力可以通过不同适配器绑定，业务层不直接拼接协议调用。

| 动作阶段 | 样例 | 必需验证 |
| --- | --- | --- |
| 感知 PERCEIVE | 读取变更、检索知识、读取标准 | 来源、范围、时效、结构与证据摘要 |
| 执行 EXECUTE | 创建评估草稿 | 参数、当前授权、来源版本、幂等身份与外部效果 |
| 验证 VERIFY | 独立读取草稿 | 目标对象、状态、版本、正文、哈希与任务条件 |

Skill 包建议包含 `manifest.json`、方法说明、输入输出定义、能力依赖、验收引用和评测样例。原有内联 Skill 可转换为 `instructions-only` 包；涉及脚本的 Skill 必须显式声明对应能力，不能通过包脚本获得未登记的 shell 权限。

### 能力效果契约

每个 `CapabilityDefinition` 至少描述：

```text
ref / version / input_schema_ref / output_schema_ref
phase / effect(READ|WRITE|UNKNOWN) / resource_resolver_ref
adapter_ref / timeout / credential_scope_ref
idempotency / precondition / reconcile_ref / verifier_refs
approval_policy_ref / compensation_policy_ref
```

`UNKNOWN` 表示效果未完成治理，新绑定默认拒绝执行，不能按只读对待。MCP 的 `readOnlyHint` 等字段是服务声明的提示，不能单独作为可信权限依据；这一点也与 [MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) 的信任要求一致。

### 收敛原生 MCP 通道

当前业务草稿已受 Gateway 保护，但不能由此推断任意 MCP 工具也具备同样的授权、幂等和核对保障。分两类处理：

- **已治理的只读能力**：可以保留模型原生调用体验，通过 `ReadCapabilityProxy` 暴露稳定工具名；代理校验主体与资源、调用预算、脱敏与证据保存。模型获得代理工具，不直接获得任意上游凭据。
- **有副作用的能力**：由模型生成 `ActionProposal`，统一走现有意图、授权、分发、核对和验收链。即使底层是 MCP，也不允许在认知进程里直接写入。

只读分类需要受信适配器、服务权限和测试共同支撑，防止同名工具换实现。MCP 的动态工具目录变更或 Schema 漂移应使绑定失效，重新审核/发布能力版本。

CLI 业务适配器使用受信的参数构造器和参数数组，不接收模型提供的完整 shell 命令。模型服务的 Codex/Cursor CLI transport 继续作为认知适配器管理，与业务 CLI 能力分别配置凭据、预算和审计。

## 六 保持执行 验收 恢复的确定性

保留现有内核顺序：固定版本与任务 → 规划/提案 → 参数与范围检查 → PREPARED 意图落盘 → 执行时授权 → DISPATCHED → 外部调用 → 保存观察 → 独立验证。

必须继续满足以下约束：

1. PREPARED 动作的参数、参数哈希和逻辑动作身份固定，恢复时不让模型重写。
2. 写入回执丢失或进程重启，先核对外部效果；权威确认未发生后才允许有限重试。
3. 幂等身份由运行时生成，同一逻辑动作的重试保持身份。定义版本、参数变化或新任务有新的业务含义，不能随意复用旧键。
4. 租约及 fencing 保护本地检查点，目标系统仍须提供幂等/条件写；无法核对时保留 UNKNOWN 并转人工。
5. 业务验收采用独立读取与确定性规则。模型的完成申请、报告措辞或反思结果不能覆盖失败验收。
6. 取消先停止后续动作，对在途写入核对，保留残留影响。补偿若存在，也是单独受控动作，不隐含承诺回滚。

“大脑”因此分为认知组件和运行内核：前者可以有模型差异，后者负责可恢复事实。审计保存决策摘要、证据、动作及判断理由，不依赖保存模型私有思维链来恢复任务。

## 七 样板场景如何贯通新模型

| 步骤 | 变更评估中的行为 | 沉淀的工程对象 |
| --- | --- | --- |
| 受理 | 验证主体、项目、test 环境及本次目标 | TaskContract |
| 岗位绑定 | 绑定变更评估岗位、职责、方法与标准 | CompiledAgent + DomainPack |
| 准备知识 | 检索当前发布规范和适用经验；过滤越界、过期与候选条目 | ContextManifest |
| 感知 | 通过注册读取能力获取变更、依赖、测试和回滚方案 | 带来源版本的 Observation |
| 认知 | 生成计划与风险报告，标注引用和证据缺口 | Decision / Report |
| 本地验证 | 检查章节、关键事实和风险规则 | VerificationResult |
| 执行 | 提案创建草稿，授权绑定具体参数后写入 | ActionIntent / EffectReceipt |
| 回读与恢复 | 回执丢失时按原键核对；对正文、状态与版本独立验收 | Evidence + TaskOutcome |
| 学习 | 保存运行情节，生成“写入不明先核对”的经验候选 | EpisodicMemory + ExperienceCandidate |

经验发布后，新任务可检索其适用条件，但 UNKNOWN 写入先核对仍是内核规则，不能依赖是否召回到这条经验。

| 异常 | 目标行为 |
| --- | --- |
| 标准过期或同级规范冲突 | 停止作出通过结论，说明需要补充或裁决 |
| 私有记忆跨租户或主体召回 | 在上下文构建前拒绝，记录排除理由 |
| 经验候选被模型推荐 | 候选不进入正式执行上下文，不自动晋升 |
| MCP 工具被标注只读但实际要求写权限 | 按正式效果契约及服务权限限制拒绝，不信任提示字段 |
| 写入成功但响应丢失 | 原键核对，不再 create；无法核对转人工 |
| 修改 Agent 后恢复旧运行 | 使用旧配置快照，仍检查当前授权 |
| 接口/标准变更导致验证器不兼容 | 阻止新绑定；旧运行按已发布版本与当前禁用策略处理 |

## 八 存储 API 与模块改造

继续使用模块化单体和 SQLite，不先拆成多个服务。建议新增以下逻辑表：

| 表或集合 | 关键键与用途 |
| --- | --- |
| `agent_definitions` / `compiled_agents` | 租户 + Agent + 修订；岗位与编译快照 |
| `domain_packs` / `capability_definitions` / `skill_definitions` | 租户 + 引用 + 版本；发布依赖与适配器绑定 |
| `asset_versions` / `asset_access_policies` | 租户 + 资产 + 版本；来源、正文摘要、时效和访问策略 |
| `context_manifests` / `context_items` | 租户 + 运行 + 认知轮次；被使用的引用及哈希 |
| `episodic_memories` | 租户 + 记忆；指向既有运行与证据，附保留期和可见范围 |
| `experience_versions` / `experience_evaluations` | 租户 + 经验 + 版本；条件、反例、评测、发布人和状态 |

租户必须进入主键、唯一约束、外键及查询条件。元数据事务复用当前 Store 的连接与 fencing 规则；资产正文可先存在本地受控文件目录，索引只保存引用。明确跨数据库/对象存储的写入和删除恢复策略，避免一边已发布、一边正文缺失。

建议 API 分组：

- `POST /api/agents/{id}/compile`：解析引用并返回诊断，不产生授权。
- `GET /api/capabilities`、`GET /api/skills`、`GET /api/standards`：返回当前主体可见的已发布条目。
- `POST /api/knowledge/search`：带主体和任务范围的检索；身份从服务端获取。
- `GET /api/runs/{id}/context-manifests`：解释每次认知用到的资料与排除原因。
- `GET /api/experiences`、`POST /api/experiences/{id}/evaluate`、`POST /api/experiences/{id}/publish`：候选、评测和受权发布分别记录。

以上为拟新增接口，当前 Web API 不应被文档误认为已支持。实际检索接口的身份、策略与限流由服务端校验，不接收模型自报主体。

代码改造位置：

```text
agent_framework/
  agents.py                 岗位配置与修订，保留旧 API 兼容层
  agent_compiler.py          新增：定义与依赖编译
  domains/                  新增：change-assessment 等领域包
  capabilities.py           新增：效果契约与适配器注册
  context_builder.py        新增：检索、范围、预算和 Manifest
  knowledge.py              新增：知识版本与生命周期
  memory.py                 新增：情节记忆与可见范围
  experience.py             新增：候选、评测和受权发布
  action_adapters/           新增：MCP、CLI、Python 适配
  gateway.py / runtime.py    保留：意图、授权、恢复与调度内核
  verifier.py               演进：独立验证器注册接口
```

Web UI 的 Agent 编辑器增加身份职责、标准、知识范围、方法与动作、模型配置分区；运行详情增加“上下文来源”和统一动作记录；知识页提供版本/范围/有效期，经验页提供候选—评测—发布流程。初期只显示实际已接通的功能，避免只存配置但不影响运行。

## 九 分阶段实施与验收

假设两名工程师、领域评审和现有模拟接口可用，建议按以下依赖分成四个可独立评审的交付批次。时间是估算，真实身份与业务接口改造另计。

| 批次 | 工作与具体落点 | 完成标准 | 参考工作量 |
| --- | --- | --- | --- |
| P0A 定义统一 | `agents.py` 兼容层、AgentCompiler、现有场景 DomainPack | 旧配置可转换；编译诊断明确；原有任务与模型快照可恢复 | 3–5 人日 |
| P0B 动作治理 | CapabilityRegistry、MCP/CLI 适配与只读代理、Gateway 泛化 | 所有写入均有持久化意图与当前授权；原生写调用被拦截；四工具故障用例等价通过 | 5–8 人日 |
| P1 知识上下文 | 资产版本、受控检索、Manifest、来源展示 | 跨租户、过期、冲突及注入用例可重复；每个报告关键事实可追溯到已绑定证据 | 5–8 人日 |
| P1 学习治理 | 情节归档、经验评测/发布、第二个只读领域包 | 候选默认不可用；发布和撤回影响后续检索；第二场景不修改恢复内核 | 5–8 人日 |

P0A 和 P0B 是第一优先级；二者通过后再让知识和经验驱动动作选择。若项目只投入一人，应按顺序推进，不以目录和表单数量作为交付完成依据。

迁移规则：

1. 新表和编译层先增量加入；现有 Agent 配置转换为明确的 legacy 领域包。
2. 历史任务仍保留原 snapshot，不在原记录中补写新字段或重算原哈希。
3. 新任务绑定新快照；待运行任务按版本选择旧/新路径，不能在同一逻辑动作上跨路径重放。
4. 原生 MCP 效果未分类时先限制新绑定。切换执行策略前排空或明确处置在途任务；当前策略撤销可阻止历史任务继续发起危险调用，保留未决效果供核对。
5. 知识清单可先影子构建，与当前上下文对比；影响决策的灰度应以独立任务运行和可核对产物验收，不能偷偷替换生产任务证据。
6. 回退只影响后续路由；已发送写入必须先核对外部结果，不能靠回滚代码重置动作状态。

后续再根据实际瓶颈决定分布式存储、独立队列和多 Agent。多 Agent 采用父子 TaskContract、明确委托能力、子任务预算和汇总验收，子 Agent 的授权不能超过父任务；单场景闭环未稳定前不增加角色数量。

## 十 后续实现的验收矩阵

| 维度 | 必测情况 | 通过证据 |
| --- | --- | --- |
| 定义与兼容 | 旧 Agent 转换、缺少引用、未知验证器、编辑后恢复 | 编译诊断、快照摘要、旧任务结果 |
| 知识隔离 | 跨租户、跨项目、私有偏好、缓存混用 | 资料未进入模型上下文及排除日志 |
| 知识质量 | 过期、冲突、来源版本变化、摘要不一致 | Manifest、证据版本与停止原因 |
| 动作治理 | 原生 MCP 写入、CLI 参数注入、动态目录变更、授权撤回 | 分发前拒绝且外部零副作用 |
| 可恢复写入 | 响应丢失、写后崩溃、租约被替代、权威不存在、无法核对 | 原键保持、调用计数、目标库行数和确定性核对事件 |
| 学习治理 | 未审核候选、失败反例、过期经验、撤回发布 | 正式检索只使用适用的已发布经验 |
| 完成判断 | 模型声称完成但缺证据、回读内容被改动 | 独立验收拒绝，状态保留为待处理 |
| 扩展性 | 新增只读领域包、模型切换、协议切换 | 核心恢复逻辑不因业务字段变动而改写 |

指标同时记录端到端成功率、误报完成率、固定故障集的重复副作用数、恢复正确率、有效知识召回、上下文 token 与单次成功成本。试点阻断项为固定权限和故障集中的已知越权、重复写入与误报完成；这不构成开放环境中的绝对保证。

成本和延迟应分别记录运行内核、知识检索、模型、工具及等待人工的耗时；与当前样板的同一组输入比较，报告样本数量和失败分布。检索、反思和角色增加可能提高总成本，需要测量后再推广。

## 十一 可运行的设计样例

目录 [design/agent-v2](../../design/agent-v2/) 提供模拟岗位定义、相关注册数据与标准库验证器，不调用模型、数据库或业务工具。

```bash
python3 design/agent-v2/validate.py
python3 design/agent-v2/validate.py --self-test
```

第一条生成已解析引用的设计快照，明确 `execution_authorized: false`。第二条检查 12 个独立反例：跨租户、跨项目、无读取权限、知识过期、未发布经验、未知能力、写入缺少核对、原生写入绕过、模型提供幂等键、未知验收器、缺少标准证据和知识内容篡改。

样例验证引用关系与关键边界，不能替代完整 Schema 校验、真实 IAM、上游工具效果评测或执行时网关。该设计样例不参与运行。后续 P0A/P0B 已接入运行时和工作台，实施范围、兼容策略与验证见 [P0 实施说明](../p0/implementation.md)；后续 P1 知识、记忆、经验治理及第二只读领域包也已接通，见 [助理实现](../assistant/implementation.md)。

## 十二 设计依据
