# 智能体原提交重试与后续修改保留

2026-11-02。当前源码改进，尚未发布。

此前保存失败后只保留请求编号，重试会从当前表单重新组装内容。用户继续修改后，同一编号可能带上另一份内容；如果原提交尚未被服务受理，无法明确重试最初提交。只读核对暂未找到回执时，也不能据此认定原请求已经结束。

## 当前操作

首次保存固定原请求的目标智能体、配置内容、版本和编号。本页后续输入另外保留，不修改这份原提交。再次点击普通保存时，若本页已经变化，会提示先核对或明确重试，不发送混合了新输入的请求。

“重试原保存，保留本页修改”使用原内容、原编号和原目标。后续输入即使有空指令、未完成职责或无效 MCP JSON，也不会阻止核对原提交；重试成功后，若本页已变化，窗口保持打开，用户可以继续修正，再按核对版本保存、另存副本，或明确使用服务中的配置。

| 结果 | 后续操作 |
| --- | --- |
| 暂未找到回执，结果仍未知 | 可稍后核对或重试原提交；即使能读取当前配置，也不开放换号保存、另存或采用结果 |
| 首次提交明确被拒绝 | 可以核对当前配置，或“保留修改，重新准备保存”；重置本身不写入服务 |
| 之前结果未知，重试又被拒绝 | 继续保留未知状态，不把后来的拒绝当作原请求从未受理的证明 |
| 找到匹配的保存回执 | 显示接受版本和当前版本，按现有冲突及归档规则明确处理本页输入 |
| 回执编号、目标或接受版本不匹配 | 保持窗口和未知状态，不显示保存成功 |

核对只读服务数据。所有实际保存仍由用户发起，并继续受服务端的版本、归档、身份和空间校验约束。未知结果不能通过更换编号绕过原请求；明确另存副本仍需先解决原请求。

## 刷新与旧副本

当前标签页的恢复记录升级为 v2，在同一作用域键中同时保存原提交字符串、原编辑快照与本页后续输入。写入发生在 POST 之前，刷新后不会自动重发。服务回执不写入本地记录，恢复后须重新读取服务确认。

v1 副本继续可读。它只有保存编号，无法恢复不存在的原提交内容，因此界面明确提示这一限制。普通保存不会自动推断原内容；用户可以先核对，或明确选择“用本页输入和原编号重试”。此操作仍复用旧编号，若服务已接受另一份内容，会返回冲突并要求核对。

恢复记录总上限仍为 500,000 字符；原请求和编辑快照分别限制为 200,000 字符。损坏、越界、目标或版本不匹配的记录不用于重试。存储不可用时继续说明刷新可能丢失并保留当前窗口。

保存与读取回复同时检查编辑会话、租户、操作人和空间。迟到的响应及其清理逻辑不能采用到另一份编辑，也不能解锁另一个正在保存的窗口。

## 验证

改动前新增的四个行为测试全部复现失败：原提交被后续输入替换、未知结果可凭最新配置换号、未完成 MCP JSON 阻止原提交重试、迟到响应解锁另一会话。实现后新增 14 项逻辑测试通过，覆盖上述行为、错误回执、拒绝状态、身份变化、v2 持久化和 v1 兼容。

浏览器在临时合成服务上验证了未送达与已受理响应丢失两种情况，比较重试前后的完整请求内容与编号，模拟原请求在核对后才受理，并检查配置数量与版本不会重复增加。另覆盖刷新、原提交和未完成输入分离、旧副本显式重试，以及浅深主题、四档桌面宽度、两倍文字共 16 组布局和键盘操作。
