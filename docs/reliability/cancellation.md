# 任务停止的持久请求与恢复

2026-10-30。当前源码改进，尚未重新生成发行包。任务停止从进程内通知改为先保存停止请求，再由执行器或恢复进程处理。

## 使用

- 点击“停止本轮”后，界面显示“正在停止”。此时请求已保存，当前操作可能仍在结束和核对；只有运行实际进入终态后才显示结果。
- 刷新、断开实时连接或服务重启后，仍能查看同一停止请求和已保存片段。未完成片段保留明确标记，输入草稿继续保留。
- 停止只作用于当前轮次。已经明确发送并排队的后续消息，等本轮结束后按顺序处理；未发送草稿不会自动提交。
- 停止处理意外失败时，显示“停止处理受阻”和“重试停止”。后台等待显式重试，不自动反复执行；恢复原任务或新增授权不能覆盖待处理的停止请求。
- 任务已完成时保留真实结果。接受停止请求不等于已取消，不会把已经成功的任务改写为取消。

在途业务操作可能已经产生效果。执行器先核对已发出但结果未知的写入，再结束本轮；无法确认时保留 `NEEDS_REVIEW` 等实际结果。停止不会撤销已经确认的业务效果，也不会重置任务身份、冻结配置、预算、截止时间或授权。

尚未开始的后续消息使用“取消排队”。提交时会再次检查该轮是否已创建运行；若已开始处理，提示改用停止当前轮次，避免把实际运行中的消息误记为排队取消。两个动作的事务规则见 [任务提交与取消排队](task-submission.md)。

## 请求、执行与恢复

`POST /api/runs/{run_id}/cancel` 先在数据库事务中保存请求，再通知当前进程。响应返回任务详情；异步请求返回的 `202` 表示已接受处理，不承诺已经停止。CLI 的 `cancel` 同样先保存请求，其他进程持有任务时也能接受；运行租约释放或过期后继续处理。

请求独立于活动运行检查点保存，不修改正在执行的任务版本或租约，避免因用户点击停止而破坏执行器的下一次合法保存。运行循环和模型传输检查数据库中的停止意图；本机事件仅用于加快响应。检查采用短时缓存，执行步骤边界会重新读取。

已在普通执行队列中等待的任务尝试取消尚未开始的执行器，并通过执行轮次阻止旧排队任务晚到接管。停止收尾使用独立、容量受限的工作池，避免普通执行槽位全部占满后停止也无法开始。

后台按未完成请求索引恢复，检查租约、租户、工作空间及操作人范围。重启或原进程退出后，等待原租约释放或过期再接管。待处理请求只进入停止收尾，不恢复正常模型执行。正在停止的工作流节点暂停流程推进，每日任务和对话恢复也会识别停止意图。

停止错误保存安全说明，刷新或重启后仍保留。显式“重试停止”沿用原请求时间并增加尝试代次；旧尝试晚到的失败不能覆盖新尝试或已经完成的结果。现有执行器遇到停止错误后退出本次工作，避免反复循环。若旧版本进程已经将运行保存为终态，却未结清停止请求，恢复扫描会按真实终态补齐记录并清除旧错误。

## 持久化与展示

新增 `run_cancellations` 表，以租户和运行 ID 为主键，保存：

| 字段 | 含义 |
| --- | --- |
| `generation` | 停止尝试代次，首次为 1，仅显式重试增加 |
| `requested_at` | 首次接受请求时间，重复点击和重试均保留 |
| `updated_at` | 当前请求最后更新时间 |
| `requested_by`、`source` | 操作人及请求入口；Web 为 `web`，CLI 与执行器沿用 `runtime` |
| `error` | 停止收尾的安全错误说明 |
| `completed_at`、`outcome` | 实际结束时间及运行终态 |

同一待处理请求重复提交不重复创建记录或审计。审计事件包括 `run.cancel_requested`、`run.cancel_retried`、`run.cancel_failed` 和 `run.cancel_completed`。运行终态检查点与停止完成记录在同一事务中保存。

API 通过 `cancellation.pending`、`error` 和 `outcome` 表达请求状态。列表、对话与运行检查页展示派生的 `CANCELLING`；停止失败展示为中断待处理，实际内核执行阶段继续保留。列表更新时间取运行与停止请求的较新值，迟到的页面回执不能覆盖更新后的内容。待处理停止时隐藏恢复执行和新增授权入口，仍可撤销已有授权。

备份保存请求表和索引。恢复后的未完成请求仍按停止处理，不当作普通任务续跑；业务幂等事实继续保留。有关中断诊断与完整备份说明，见 [执行器中断恢复](worker-recovery.md) 和 [核心数据备份与恢复](../data-protection/implementation.md)。
