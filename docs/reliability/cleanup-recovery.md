# 清理异常保存后的中断恢复

2026-11-03。当前源码改进，版本仍为 1.3.0，尚未发布。

在模型清理失败之后，原实现先保存诊断，再保存失败或停止结果。如果执行器在两次保存之间退出，原运行仍为 `RUNNING`；恢复会再次进入模型调用。三项失败基线均观察到调用次数从 1 增加到 2，覆盖清理检查点、首个模型失败事件，以及仅有旧版事件记录的恢复。

## 当前行为

首个带有清理异常的 `model.failed` 事件与运行中的清理状态、原错误码一起提交。后续保存 `model.cleanup_unconfirmed` 时同样保留错误码。这样，执行器在任一检查点后退出，都有持久事实说明原模型调用已经失败。

恢复取得有效租约并验证冻结快照后，先处理尚未结束的清理异常，不进入新的模型调用、上下文准备或原业务动作派发。只有已经派发且结果未确定的业务写入，才通过现有回读通道核对；回读不存在、保留了未执行的准备意图，或回读后再次中断，都不会重新创建写入。

没有待核对业务效果时，按已保存的错误结束原轮次；已经发生或仍无法确认的效果保留为人工核对。停止请求优先处理，冻结的期限、预算和当前回读权限继续生效。期限已经耗尽时仍按期限结束，原模型错误码保留在清理记录中，不重置预算。已失去执行权的旧执行器仍先传播租约异常，不能替接手执行器写入结果。

旧记录仅有 `model.failed` 中的清理信息时，按该运行的事件索引读取最后一条相关诊断并恢复状态。只有清理信息、无法找到对应原错误码时，明确使用 `model_cleanup_failed`，不猜测原因。已结束的运行继续返回原结果。普通执行器中断没有清理失败时，沿用原恢复方式。

运行状态中的 `cleanup_model_error` 保存原错误码，`model.cleanup_recovery_started` 记录开始处理原异常。认知入口还会直接拒绝带有清理失败标记的调用，避免其他调用路径绕过恢复次序。

## 用户流程

任务工作台将这类恢复显示为“核对并结束本轮”，说明它会核对已发生的操作并结束原轮次，不重新调用模型。异常处理尚未结束时，暂不提供环境确认勾选。原轮次结束后，继续使用[环境核对](cleanup-review.md)：用户实际检查本机环境并确认，才允许后续排队消息或新的重试继续。

恢复操作回执丢失后，刷新可读取已保存的原轮次结果。后续环境确认仍绑定结束后的运行版本；中断时的旧版本不能解除新检查点上的暂停。原始错误、公开片段、排队消息与未发送草稿保留。

## 验证

新增 12 项后端测试覆盖两个中断窗口、旧版事件恢复、取消优先级、失效执行版本、实际模拟业务系统中的一次写入与回读、回读不存在、回读之后第二次中断、回读被当前权限拒绝、恢复时期限耗尽、旧记录取消，以及认知入口保护。普通执行器恢复、清理失败、租约失效、取消和环境核对测试一并回归。

浏览器使用真实隔离模型子进程：先输出公开片段，再注入终止拒绝，最后在清理状态已保存而终态尚未保存时注入执行器异常。页面刷新保持中断状态，模型调用次数为 1；点击“核对并结束本轮”后丢弃成功的 HTTP 回执，再刷新，原运行按 `model_timeout` 失败结束，调用次数仍为 1。独立观测确认，此时本地管道已关闭，但测试子进程仍存活。恢复没有将它误报为已结束，也没有接续队列。

测试随后显式结束自己创建的子进程，再模拟用户环境确认。只有一条原排队消息开始并成功完成，总模型调用次数变为 2；原失败轮次的调用次数仍为 1，公开片段和草稿保持不变。没有真实模型服务或业务系统调用。

## 边界

本轮处理已经保存的清理失败事实。没有写入任何诊断前发生的进程级中断，仍由原有执行器恢复机制处理。框架不依据历史 PID 自动发信号，也不将用户环境确认当作独立验证进程退出的证明。

当前业务工具仍是模拟实现；回读、持久化、租约及禁止重复派发是真实代码。发布候选与源码和资源逐项校验，未发布，未重复全新环境安装。
