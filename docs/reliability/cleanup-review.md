# 清理未确认后的队列暂停与环境核对

2026-11-03。当前源码改进，版本仍为 1.3.0，尚未发布。

上轮已经使本地管道关闭独立于进程终止结果，并保留原始错误。但模型调用失败或停止后，对话派发器仍可能继续已接收的消息；真实进程尚未结束时，会再次启动模型。本轮将清理未确认纳入后续执行的暂停条件，并提供完整恢复入口。

## 当前行为

只要当前任务任一轮存在未核对的清理失败，后续消息暂停。新消息和失败轮次重试在受理事务内拒绝；已经排队的消息不丢失，已经创建但尚未执行的后续轮次也不再派发。创建新轮次时再次检查，防止预检之后出现的清理失败被漏过。已接收消息的重复提交仍返回原记录，查询回执和取消排队继续可用。

任务工作台展示需要检查的轮次、当时记录的进程编号及管道关闭情况。任务列表显示“需要核对”，排队状态不会遮盖问题；处理前不能归档。停止后的轮次保留停止结果，同时明确提示进程清理仍需检查，不直接承诺可以继续发送。只有一轮的任务也保留对话与核对入口。

用户在本机检查并处理环境后，勾选“我已检查本机运行环境，允许继续后续消息”，再确认继续。确认会接续已有排队消息，并恢复发送和重试；其他待核对的业务操作仍会阻止后续执行。界面明确说明这个后果。

确认记录绑定租户、任务、运行编号和运行版本，保存操作主体、空间及时间。事务内复核运行已结束、租约已释放、版本未变化。两个页面或应用实例确认同一版本，只保存一条记录；旧确认不能解除后来出现的新故障。原运行状态、原始错误和清理失败信息保持不变，确认是用户允许继续的记录，不是操作系统进程退出的证明。系统不会根据历史进程编号再次发信号。

确认回执丢失后，当前标签页保存原运行编号与版本，刷新后提供只读核对。查询确认记录和任务详情使用同一数据库快照；查到原记录后无需重发，暂未查到时仍需重新检查并明确勾选。不会自动提交确认。迟到回执不能切换当前任务，也不能删除另一运行版本的待核对副本。

## 接口与存储

- `GET /api/tasks/{task_id}/cleanup-review`：只读返回当前任务详情和已保存的环境确认记录。
- `POST /api/tasks/{task_id}/cleanup-review`：接受 `{run_id, version}`，复核范围与状态后保存确认。
- `task_cleanup_reviews`：以租户、运行编号、运行版本为唯一键；核心数据库备份与恢复保留它。
- `model.cleanup_reviewed`：记录检查主体与允许继续的决定；不写入“进程已停止”或“任务已完成”的声明。

任务详情和完整对话导出包含待核对轮次，Markdown 导出也说明后续消息暂停。只读检查没有新增表的旧数据库时，将清理失败视为尚未核对，不迁移原数据库。查询使用当前任务及其轮次编号定位运行，已检查查询计划使用租户与运行编号索引，不遍历无关运行的正文和审计记录。

## 验证

后端覆盖首轮失败与停止、后续轮次失败、已创建但未执行的下一轮、受理期间状态变化、两个实例并发确认、保存成功但派发失败、原版本重放、新故障版本拒绝、其他主体或任务隔离、业务操作继续待核对、重启、备份恢复、历史只读检查和 HTTP 接口。

浏览器使用真实隔离模型进程，输出公开片段后保持存活，并注入终止拒绝。独立观测验证：本地管道关闭，但子进程仍活着；两条已接收消息未开始执行。用户可取消其中一条、查看原回执和诊断，刷新后另一条仍暂停，草稿保留。测试显式结束自己的进程，随后模拟用户环境确认，并丢弃已成功确认的 HTTP 回执。刷新和只读核对恢复确认结果，剩余消息只执行一次，已取消消息不复活，原失败记录保留。

桌面验收覆盖浅色、深色、1024/1440px 和实际 28px 文字。提示区域增高时页面可滚动，确认控件与输入区均可到达。首次浏览器回归发现首轮暂停落入旧详情分支，已修复并增加单元测试。旧清理脚本原先在失败后输入草稿，本轮改为实际在调用期间输入，再验证暂停后保留。布局测量改在同一次 DOM 读取中滚动并取尺寸，避免后台刷新使验收持有已移除元素；页面刷新保持开启。

## 边界

环境核对只覆盖当前任务及其轮次，不是本机所有任务的全局故障开关。确认依赖用户实际检查运行环境；框架不会声称已独立验证进程终止，也不会用持久化 PID 自动清理未来可能复用该编号的进程。

浏览器核对副本属于当前标签页；存储受限时提示保留页面，服务器上的已接受确认不受影响。测试使用临时数据库和合成模型，没有调用真实模型服务或业务系统。候选包仅核对源码和包内容，没有发布或重复全新环境安装。
