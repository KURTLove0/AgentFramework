# 续问历史与来源核对

2026-11-02。当前源码改进，版本仍为 1.3.0，尚未发布。

此前模型历史直接携带每条报告的完整引用。若上一轮对同一份长资料重复引用，多份引文可能单独超过 96,000 字节的历史预算，导致下一轮连上一轮简短的正文也收不到。验收用一份约 12 KB 的合成资料和八条有效重复引用重现了这个问题。

## 当前行为

送入续问的历史保留回答正文，将引用压缩为资料标识与内容摘要；同一消息内相同的标识和摘要只保留一次。原报告、全部引文和审计记录继续保存，页面仍展示原报告。生成历史时，有引用的报告继续用原执行配置和证据核对，未通过的正文改为来源失效提示。

历史按照轮次在同一数据库读取快照中分批组装，无引用的轮次不装载完整执行、动作和经验候选。有引用的轮次仍读取所需的完整证据，不绕过原有检查。子轮次的操作者和项目归属必须匹配。窗口保留最近连续的消息，最多 200 条、96,000 字节，预算包含 JSON 数组的括号和逗号。完整历史摘要通过逐条累积计算，省略数量继续随上下文提供。

每次模型调用前重新核对历史中的显式引用。资料撤回、过期、内容摘要变化或不可访问时，相关回答正文被替换为提示。同一次核对中每个资料标识只读取一次，各消息的预期摘要仍分别核对。旧版已冻结上下文中的重复引文也会在调用前压缩，原冻结记录不被修改。

持久化上下文清单分别记录原历史摘要与实际发送上下文的摘要，并记录发送消息数量、省略数量和来源失效轮次。这使审计能区分创建轮次时的历史与调用时重新核对后的输入。

## 同一份历史的测量

脚本 `tests/measure_history_context.py` 复用带标记的 60 轮合成数据库。此组报告没有引用；新旧代码各测量三次，均输出 119 条消息、15,216 字节，上下文 SHA-256 相同。

| 指标 | 改进前 | 改进后 |
| --- | ---: | ---: |
| SQL 语句数 | 300 | 1 |
| Python 累计解码的 JSON 输入 | 1,074,238 字节 | 5,291 字节 |
| 组装耗时中位数 | 59.0 毫秒 | 4.7 毫秒 |
| Python 跟踪分配峰值中位数 | 205,247 字节 | 94,741 字节 |

这是开启 JSON 解码计数和 Python 内存跟踪时的历史组装测量，不包括模型延迟、SQLite 原生内存或整个 HTTP 请求，也不代表带引用报告的相同加速比例。

## 验证与边界

新增 12 项回归覆盖重复长引文、精确预算、Unicode 序列化、完整历史摘要、取消的排队消息、跨批次并发快照、范围隔离、旧格式引用、共享资料和不同摘要、无效引用结构以及实际发送历史的审计对应关系。

浏览器验收通过真实页面发送续问，在排队后撤回真实临时资料，检查模型替身收到的上下文、原报告、冻结历史、持久化清单和调用次数。仅模型输出为固定替身；测试使用隔离数据库，没有调用真实模型。

预算约束针对消息数组。单条正文自身超出预算时仍可能被省略；本轮没有加入摘要生成、拆分正文或语义压缩。来源检查依赖显式引用，不能推断无引用改写中的间接来源。新旧格式不会改变已经冻结的历史记录。

最终测试、候选包与源码摘要见 [验收记录](history-context-verification-20261102.json)。候选包未发布；本轮未重跑全新环境安装验收。

最终通过 1055 项后端测试、787 项前端测试，以及历史上下文、消息提交和实时对话三组浏览器验收。候选包的 141 个程序文件与当前源码一致，包内 wheel 与单独 wheel 相同，内外校验清单通过。
