# 工作流恢复与执行可靠性

执行器异常的后续处理见 [中断诊断与显式恢复](worker-recovery.md)：错误跨重启保留，停止后台反复重试，恢复使用原任务并校验执行轮次。

2026-10-29。本轮完善工作流在队列拥堵、服务重启与节点对话结束时的接续行为。改动位于当前源码，尚未重新生成发行安装包。

## 用户可见的行为

- 已接受的工作流在 `CREATED` 或 `RUNNING` 状态下失去执行进程时，服务会在执行位置可用、相关租约释放后接续原运行。
- 节点补充回答成功，并且后续排队消息全部处理完成后，流程会使用最终完成的回复继续。首次续跑通知遇到队列已满、父流程仍忙或服务退出时，后台检查会再次发现这项工作。
- 历史超过 100 条时，较早工作流仍可接收节点补充回答并继续；界面历史显示数量不再决定恢复范围。
- 工作流等待授权或材料、手动保存进度、故障注入中断时，继续保留对应的授权、补充或恢复入口。普通工作线程异常不会在同一服务进程中被反复重试；临时租约竞争在租约释放后可接续。
- 持久化取消请求在重启后继续处理。尚未开始的流程会直接取消，不启动节点。

原运行 ID、Agent 配置、上游输入、已采用的输出轮次及节点任务身份继续冻结。恢复时仍由原执行器校验来源和结果，并沿用授权、幂等与未决写入核对规则。

## 执行与关闭

服务每轮对话调度后检查工作流，间隔约一秒。检查按租户、当前用户及可用工作空间筛选已保存记录，受现有 16 项执行队列上限约束；其他进程持有父流程或节点租约时等待后续检查。等待节点对话完成的流程只在收到成功结果、且没有运行或排队中的后续消息后接续。

恢复检查与用户启动请求发生竞争时，共用已有执行任务，不额外提交一次，也不把已经接受的启动误报为重复执行冲突。某一流程快照异常会记录本地错误，不阻断其他有效流程恢复。

所有工作空间视图共享服务关闭信号。服务关闭后，后台任务不再向已退出的执行器提交新工作。执行器拒绝提交时，任务记录会释放“正在执行”的占位，用户仍可明确重试。

## 持久排队与准确反馈

第二轮继续处理了一个边界：授权先保存、队列已满后报错，可能让流程仍停在等待授权；手动恢复在队列拥堵时也可能只留下报错。现在启动、授权、恢复和取消都会保存待执行请求，队列容量只决定何时执行。相关接口在拥堵时返回 `202`，页面显示“排队中”，刷新后保留同一运行和请求状态。

流程创建和初始派发请求一起提交；具体提案授权与继续执行请求也在同一个事务提交。任一步写入失败会回滚整次授权，不留下没有续跑请求的半完成操作。取消标记与停止请求采用相同的提交方式。

每个待执行请求带有版本。执行器只确认自己接手的版本，节点等待授权状态刚保存时收到的新授权不会被较早的执行器清除。原持有者失去租约后也不能清除新执行器的请求。重复尝试入队会复用已保存请求，历史运行和节点身份继续保持不变。

队列不自动延长授权期限。排队期间授权过期，恢复后仍停在等待授权，未产生草稿；用户重新审查并授权后才继续。执行器拒绝提交会保存错误状态和审计事件，重启后仍提供明确的“继续 / 恢复”入口，避免反复自动提交失败请求。重试后保留此前入队失败的审计记录。

列表与详情通过文本区分排队、正在取消和等待重试。授权排队时，节点也显示为排队，并注明授权已保存，避免重复授权。排队期间保留取消入口；具体进展通过一条完整、可访问的状态提示呈现，未将每个状态标签都设置为独立播报区域。
