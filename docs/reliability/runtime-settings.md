# 运行时配置保存与恢复

2026-11-03。源码改进，版本保持 1.3.0，尚未发布。

运行时配置此前只有版本冲突检查。保存已提交但响应丢失时，页面不能确认原保存；重新加载会替换本页输入，迟到响应也可能影响后来打开的表单。本轮增加持久保存回执、当前标签页草稿和明确的冲突处理。

## 编辑与恢复

运行时配置由同一租户的工作空间共享。编辑中的模型、超时、修复次数、推理强度及默认运行时会保留在当前标签页；离开页面、切换工作空间或刷新后可以继续。恢复不会自动保存或调用模型。

进入页面会读取当前配置。若本页已有修改，读取期间新输入的文字也会保留。当前版本与编辑基准不一致时，展示当前已保存的配置，并提供：

- **采用当前配置**：明确放弃本页输入，使用服务端当前值。
- **保留输入，按当前版本继续**：保留本页输入，以核对过的版本作为基准，之后再点击保存。

“核对当前配置”同样保留未保存输入，不直接替换整个表单。创建智能体仍使用已保存配置，未保存的参数继续作为草稿保留。

草稿按租户、用户和浏览器标签页保存；不作为服务器上的共享配置，也不承诺关闭浏览器后长期保留。浏览器存储不可用时使用当前页面内存，并显示可展开选择复制的本页配置。格式错误的恢复记录不会自动应用或提交，可明确清除后重新读取。

## 保存编号与回执

每次新保存生成一个编号，冻结本次内容和基准版本，并在发送前保留恢复副本。配置版本与不可变回执在同一个数据库事务内提交。重复提交同一编号和同一内容只返回原回执；用同一编号提交不同内容会被拒绝。两个页面同时修改同一基准版本，只有一个版本能够提交。

保存响应丢失或连接失败时，先“核对原保存”。核对是只读操作：

- **查到原保存，当前仍为该版本**：确认提交结果，保留核对期间新输入的后续修改。
- **查到原保存，但配置之后又变化**：分别显示原保存接受的版本与当前版本，要求明确采用当前配置或保留输入继续。
- **尚未查到原保存，当前仍是原基准版本**：可“使用原内容重试”，继续使用原编号与原参数。此时表单中的后续修改不会被误当作重试内容。
- **尚未查到原保存，当前版本已前进**：展示当前配置与本页输入，核对后可按当前版本继续。原请求的旧基准版本已无法覆盖新版本。

服务端明确拒绝无效参数时，保留原始输入并释放本次提交，修正后可重新保存。保存成功只代表配置已落库；已有任务恢复继续使用它们原来冻结的配置。

## 页面与异步保护

保存、核对与重新加载均绑定当前表单、路由、工作空间、租户和用户。离开后旧请求仍可能在服务端完成，但迟到响应不能改写新表单、清除新保存的等待状态或删除新草稿。返回时通过保留的编号核对实际结果。

等待模型目录时新选择的模型和推理强度会保留，目录响应不会用请求发起时的旧值覆盖它们。目录里已没有的原配置继续明确显示，方便核对。

恢复操作使用可聚焦按钮、明确的状态说明和展开比较；核对完成后保持合适的键盘焦点。相同输入的重复 `change` 事件不重建恢复按钮，避免输入框失焦时吞掉用户刚点击的“核对”。

## 接口与兼容

`POST /api/runtime-config` 继续接受原有的 `default_runtime`、`profiles` 和 `revision`。新版页面额外提供 `request_id`，响应包含 `found`、原保存的 `receipt`、读取时的 `settings` 与运行时目录。回执记录原基准版本及实际提交的完整配置快照。

`GET /api/runtime-config/requests/{request_id}` 按租户和主体只读核对编号，未找到时明确返回 `found:false`。回执可以跨应用重启和工作空间切换读取；不能通过另一主体或租户查询到原回执。配置内容本身继续沿用原有共享范围。

旧客户端没有提供编号时仍按原来的版本检查保存。缺少 Qoder 配置的旧请求在事务内保留当前 Qoder 参数。保存、草稿恢复和回执核对都不会创建任务或调用模型。

浏览器真实模拟已接受后丢失回执、请求未送达、之后另一次保存、切换页面后的迟到响应，以及缓慢配置读取和模型目录加载。布局覆盖浅色／深色、1024／1440 像素宽度、正常／28px 字号，检查焦点、视口边界和恢复面板溢出。已检查 [浅色核对界面](runtime-settings-light.png) 与 [深色核对界面](runtime-settings-dark.png)。相关任务配置、任务复用及智能体草稿流程一并回归。
