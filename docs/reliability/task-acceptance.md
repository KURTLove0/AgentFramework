# 任务接受时的配置一致性

2026-10-30。当前源码改进，尚未重新生成发行包。

## 解决的问题

新建任务和启动工作流此前只在预检时核对配置。另一个应用进程可以在预检结束、运行记录提交前更新或归档智能体，撤回 Skill，或修改工作流定义。旧的页面请求仍会被接受，使用用户尚未重新核对的配置。

新增回归先在原实现中复现了普通任务的五类接受竞态，以及工作流的五类接受竞态。修正后，最终核对与运行记录、首次审计、对话登记、派发意图和相应草稿清理共用原创建事务。冲突会回滚整次接受，不会排队执行或清理原草稿。

## 当前规则

| 新接受入口 | 提交事务中的核对 |
| --- | --- |
| 新建智能体任务 | 同一租户和空间中的智能体仍存在、未归档且版本一致；已启用的 Skill 仍可用 |
| 未指定智能体的历史运行接口 | 托管运行时设置的版本仍与本次预检一致，包括没有显式传入 `runtime_revision` 的请求 |
| 启动工作流 | 工作流仍存在、未归档且版本一致；所有节点智能体及其已启用 Skill 的选择仍有效 |
| 每日计划新创建任务 | 经相同的新任务入口核对；冲突按既有派发规则登记阻塞，不使用变化后的配置替代 |

工作空间是否有效也在创建事务中核对。提交期间的智能体、工作流或托管运行时变化通过 API 返回 `409`，空间已删除则按既有不可用规则拒绝。页面使用现有错误处理保留输入，核对最新配置后可以重新提交；失败的提交编号没有被占用。

已启用的标准 Skill 按绑定的固定版本核对：所属空间、包是否归档、版本是否发布、包摘要及内容是否仍与冻结包一致。发布新版本不会让旧的已发布绑定失效，也不会自动升级绑定。停用的绑定不阻塞提交。

智能体自身的模型、选项与指令来自智能体版本，不依赖未使用的全局运行时默认值。处理领域的指导也继续使用智能体明确绑定的版本，领域管理中的后续编辑不会自动替换它。

## 已接受任务的边界

配置核对只约束新的接受。相同编号已成功接受的请求，继续返回原任务或工作流回执；随后归档智能体、归档工作流或撤回 Skill，不会把原回执改成一次新的配置选择。

已接受的工作流节点继续执行流程启动时冻结的配置，已经保存的任务和历史运行继续按原快照恢复。后续对话沿用原智能体版本；后续轮次原有的 Skill 可用性、来源有效性、授权与停止规则保持原样。本次没有给历史快照新增“必须与当前智能体版本相同”的条件。

接受事务先提交时，另一个进程的配置更新会等该事务结束；任务已经接受，保留原配置。配置更新先提交时，新任务的最终核对会看到变化并拒绝接受。核对后不会再次读取配置并悄悄替换用户的选择。

## 实现

`AgentRegistry.assert_submission_current` 使用接受事务的数据库连接核对智能体与固定 Skill 包，不初始化表，不调用模型或启动外部命令。

普通新任务通过已有 `on_created` 回调，在首次审计、对话登记及草稿清理前执行核对。工作流在保存运行、创建审计和派发意图前执行核对。两种入口都保留原有重复请求的回执优先级。未指定智能体时直接比较托管运行时配置的修订号。

运行准备阶段已有的模拟数据和默认知识初始化保持原样；最终接受失败会回滚运行控制记录。真实模型执行及业务动作仍在接受成功后的执行器中开始。

没有新增表或请求字段。`Runtime.submit` 的可信冻结快照调用方式保持兼容。有关创建事务、草稿版本、接受后的恢复和停止请求，见 [任务提交与取消排队](task-submission.md)、[多页面任务草稿保护](task-drafts.md)、[每日任务恢复](../operations/daily-recovery.md) 和 [任务停止](cancellation.md)。
