# 任务列表的读取一致性

2026-11-03。源码改进，版本保持 1.3.0，尚未发布。

任务列表此前分开读取根任务元数据、最新对话状态及正文搜索结果，待处理列表又单独读取执行租约。如果另一页面在这些读取之间提交修改，一次响应会混入不同提交时刻的数据。本轮把同一任务列表响应所需的持久数据放入一个 SQLite 读快照，并统一执行器状态的观察与使用。

## 已复现的问题

修复前的三个定向测试全部失败：

- 任务处于归档状态时，另一页面恢复任务并追加消息。列表先读到旧归档标记，随后读到新排队状态，展示了实际从未存在过的“已归档且排队中”组合。
- 查询旧回复关键词时，读取任务摘要后回复被更新。搜索读取新正文，导致与同一次请求的摘要不一致。
- 执行器在列表读取过程中结束，计数、运行中筛选及行内执行器信息重新观察不同的进程状态，无法保证彼此一致。

修复后，本次响应完整保留它读取时的持久状态；下一次请求读取新的已提交数据。例如，本次仍可看到“已归档、已完成”，下次看到“已恢复、排队中”。不会为了追求实时更新而把两种状态拼到一起。

## 统一读取范围

任务列表的根任务、名称、归档、收藏、最新对话状态、取消请求、正文匹配、排序和分页边界都来自同一读连接与数据库快照。列表总量、状态计数和筛选结果继续沿用既有口径，响应结构与游标格式保持兼容。

本机执行器信息属于内存数据。在打开数据库快照前，先用短暂的执行器锁取得一次观察结果，再释放锁；计数、筛选和行内信息复用这一份结果。已退出执行器的错误继续与数据库中的执行轮次标识核对，旧错误不会归给新执行器。

待处理列表中的任务部分同时读取任务状态与租约。执行器完成并释放租约时，旧的“运行中”状态不会与新释放的租约混用，从而错误生成“需要恢复”的入口。取消失败及中断状态仍使用原有分类与操作入口。

后台计划等调用任务摘要的路径也获得一致的根任务与对话汇总。任务列表读取直接使用已经建立的存储访问对象，不重新初始化运行时，不读取完整审计、动作或执行上下文。

## 并发与兼容

SQL 查询、正文匹配与响应组装期间不持有执行器锁。隔离测试确认：另一线程可以取得该锁并提交正文更新，当前读请求仍返回自己的旧快照，下一次请求读到新正文。

摘要、正文搜索与租约查询支持复用调用方提供的连接。它们不会关闭或提交调用方的事务。自行打开的读连接在成功和异常时都会关闭；查询失败不会留下阻止后续请求的读事务。

超过 SQL 参数分批大小的读取继续使用同一快照。测试覆盖 408 个根任务，在摘要的首个批次开始时提交另一批任务的状态与正文更新，本次搜索仍保持旧状态和旧正文一致，下一次请求才看到更新。

只读历史存储缺少后来添加的名称、归档或收藏表时采用默认值，不进行迁移；没有对话注册记录的旧根任务仍可读取和搜索。

## 边界

这保证的是一次请求内的持久数据一致性。它不锁定之后的页面，也不把多次翻页变成长期数据库快照；执行中的任务仍需刷新取得新状态，现有游标规则继续生效。

进程内执行器观察和 SQLite 快照属于两种不同的数据来源，无法成为一次原子事务。本轮确保同一响应重复使用相同观察，并在其数据库快照内核对执行轮次。待处理页的工作流、每日计划和告警仍按各自读取规则获取，本轮没有声称整个跨模块页面原子一致。

## 验证

新增 16 项后端测试，包括修复前失败的三个复现、名称和状态排序、取消、执行轮次、租约与恢复入口、执行器观察、调用方连接归属、并发写入、单连接读取、异常收尾、只读兼容、跨批次一致性，以及真实 HTTP 读取期间的追加消息和正文变更。

71 项定向回归通过。浏览器验证任务历史、跨任务正文搜索、待处理入口和归档四条既有流程；没有改变界面布局或增加新的交互。完整后端回归通过 **1337 项测试**，候选包中 163 个程序文件与源码一致。详细校验见 [验收记录](task-catalog-snapshots-verification-20261103.json)。使用临时离线数据，未调用真实模型或业务系统，未发布，未重复全新环境安装。
