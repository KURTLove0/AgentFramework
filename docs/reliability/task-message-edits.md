## 使用流程

点击排队消息下方的“修改消息”，保存后原位置显示新内容及“已修改”。编辑不会暂停执行：消息可能在窗口打开期间开始处理。此时保存会被拒绝，本页文字继续保留，可核对实际要求并复制本页修改，再按需要另发补充。

关闭窗口或刷新页面后，可从“继续修改 / 核对修改”提示重新打开；即使消息已经开始处理，原编辑仍有恢复入口。同一任务在当前标签页一次保留一份未完成编辑，避免打开另一条消息时覆盖已有输入。明确结束或放弃后才能编辑其他轮次。

其他页面先修改时，本页显示冲突并保留输入。读取当前消息后，用户选择采用当前内容，或保留本页输入并基于已查看的新版本再次保存。核对是只读操作，不自动保存或重放旧修改。输入长度上限与消息一致，为 16000 个字符。

## 回执与输入保护

每次保存固定内容、预期修改版本与提交编号。保存期间继续输入，或在回执丢失后再编辑，均不会改变正在核对的原请求。重试原修改仍使用原内容和编号，成功后保留后续输入；需要再次明确保存，后续输入才会写入消息。

回执不确定时，当前标签页保留原请求和后续输入，刷新不重发。只读核对若未找到回执且原版本仍可能受理，仅提供重试原修改，不把“暂未找到”当作失败。已读取到更高版本、已派发或已取消时，旧版本无法再受理，可明确处理本页修改。浏览器无法保存恢复副本时会提示先复制文字。

原消息提交编号继续对应最初受理的文字。修改不会让发送回执丢失的页面误以为编号冲突，也不会在重试发送时把消息改回旧内容。发送核对区会说明消息已在排队期间修改，以当前对话为准。失败轮次的固定重试编号也保持此规则。

## 派发与持久化

`task_message_edits` 按租户、根任务和编辑提交编号保存回执，记录轮次、递增版本、修改前内容、新内容与时间。独立的轮次版本允许其他消息继续排队，而不让无关新增消息造成修改冲突。实际修改同时更新对话版本和审计，统一提交或回滚。

`POST /api/tasks/{task}/messages/{number}/edit` 接受 `content`、`revision` 与 `request_id`。同一事务内验证任务归属、工作空间、消息状态、是否已有运行及修改版本。只允许尚未创建执行记录的后续 `QUEUED` 消息；首条目标、取消消息、已经开始的轮次不能修改。重复编辑请求返回原回执和当前详情，不重复增加版本。

派发准备完成后、创建执行记录的事务内再次比较消息内容。若编辑先提交，旧内容的派发回滚，之后按新内容重新准备；若派发先提交，编辑被拒绝。旧准备过程中晚到的错误也不能把已经修改的队列记录标成失败。已有清理暂停和业务核对限制继续约束派发；编辑保留的消息不会解除暂停。

`GET` 同一路径可携带 `request_id`，从一致快照返回对应修改回执与当前对话，不派发任务。原消息发送回执也改为同一快照读取。旧数据库没有编辑表时按未修改读取；编辑记录与原回执随数据库备份恢复。

后续执行与对话上下文使用实际保存的消息内容。完整对话导出包含当前内容和“排队期间已修改”的版本标记；原始提交与每次修改前后的文字保存在数据库中。此版本未增加完整编辑历史浏览或回滚入口。

## 验证

新增 16 项后端测试覆盖队列身份、原发送及重试回执、编辑请求重放、并发修改、派发竞争的两个次序、旧准备错误、事务回滚、权限与输入校验、无关新增消息、只读查询、清理暂停、旧数据库、备份恢复和 HTTP。

新增 13 项前端测试覆盖编辑冻结、后续输入、未知回执、刷新、冲突、迟到响应、开始处理后的保护、任务隔离、单任务编辑草稿、存储不可用、Unicode 长度及原发送核对。测试发现并修复：重试旧修改成功后，仅比较提交期间是否继续输入会错误清理此前已修改的本页文字；现同时比较当前输入与原提交内容。

隔离浏览器实际保存、阻断和释放 HTTP 请求，验证多页面冲突、回执丢失、刷新恢复，以及派发先于迟到编辑时的拒绝和复制。释放队列后检查真实运行中的任务要求与下一轮上下文，确认内容和顺序正确。另回归消息发送、失败重试及业务待核对流程。所有执行使用模拟运行时，无真实模型或业务系统调用。

编辑冲突窗口覆盖深浅色、1024 / 1440 像素、正常 / 28px 字号八种桌面布局，并检查键盘焦点、控件边界和输入框宽度。初次截图发现通用表单布局把输入框分为半宽，已改为单列并增加宽度断言，重新完成浏览器验证。
