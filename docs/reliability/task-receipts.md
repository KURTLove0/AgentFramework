# 任务回执一致性

2026-11-03。源码改进，版本保持 1.3.0，尚未发布。

原来的新建任务页面收到 HTTP 成功响应后，会先清理待核对记录，再读取任务内容并跳转。若响应残缺或不属于本次提交，原提交编号可能提前丢失，页面也可能错误地关闭或打开不相关的任务。核对接口返回空的成功响应时，还会被当作“暂未找到”。

现在 `POST /api/tasks` 的首次受理与重复提交都会附带 `submission.request_id` 和 `submission.run_id`，与已有只读查询的字段一致。没有新增回执表，原有提交事务和确定性任务编号继续生效；内部入口显式指定的运行 ID 也原样返回。

页面在清理恢复记录前检查：提交编号与任务编号对应；任务目标、智能体 ID 与版本以及草稿回执结构有效；租户、操作人及已知项目范围匹配。创建响应还必须与本次冻结的目标、智能体版本和来源任务一致。失败时保留本页输入、原编号及刷新恢复记录，显示可核对错误，不跳转、不换号创建。

只读核对先验证回执编号、范围与必要结构。只有 `404` 表示暂未找到，残缺的 `200` 响应继续视为核对未完成。未找到任务后读取当前智能体时，也拒绝空配置、不同 ID 或无效版本，不提供错误的采用入口。

核对成功允许展示原编号先前受理的内容。这一点有意不同于创建响应：用户可能已明确采用新配置，而原请求随后才被接受。此时应找回原任务并展示其原始目标和版本，保留本页后续输入供用户选择，不能因内容不同而丢失合法回执。

## 验证

新增 **3 项后端回归**覆盖首次创建、重复提交与查询的编号一致性，内部显式运行 ID，以及真实 HTTP 创建和重放。相关后端 **33 项通过**，完整后端 **1386 项通过**。

新增 **8 项前端交互测试**，包括多种缺失和错误字段、任务编号、目标、智能体版本、来源、租户、操作人和项目范围不匹配，以及异常后的查询、刷新与同编号恢复。20 项回执测试对旧候选源码执行时 7 项失败，修复后通过。相关前端 **21 项通过**，完整前端 **1016 项通过**。

**5 组浏览器流程通过**：新增异常回执流程，以及任务提交恢复、任务复用、设置草稿与每日任务恢复。新增流程实际让临时服务受理任务，再把成功响应替换为残缺内容或错误版本；验证只读核对拒绝错误编号和空响应，合法核对打开原任务。刷新后沿用同一编号重试，任务数保持不变；错误的当前智能体配置也不能被采用。已有设置草稿与原提交分别保留，测试明确选择原提交内容后才重试。全部使用临时数据与模拟运行时，没有调用真实模型。

浅深色、1024／1440 像素宽度、正常／28px 恢复提示文字共 **8 组布局与焦点检查**通过。已检查 [浅色异常回执界面](task-receipts-light.png) 与 [深色异常回执界面](task-receipts-dark.png)。第一次浏览器检查误把已有设置草稿与原提交当作同一份目标；最终检查分别核对两份内容并明确选择重试，没有修改既有草稿恢复优先规则。

候选源码包与 wheel 已校验全部 **166 个程序文件**、内外校验和及内嵌 wheel。完整后端结果、日志和源码哈希见 [验收记录](task-receipts-verification-20261103.json)。未发布，未重复全新安装。

这些客户端检查用于防止错误确认和过早清理，服务端权限检查与提交事务仍是权威。成功回执证明任务已受理，不代表实际模型已经成功执行。旧服务缺少新 POST 回执字段时，页面会保留待核对状态；仍可通过已有只读查询核对原任务。
