# 任务提交、启动登记与取消排队

2026-10-30。当前源码改进，尚未重新生成发行包。本轮修正新任务提交与后续消息开始处理时的事务边界。

## 复现的问题

新建任务此前先保存运行，再登记对话和首次自动启动。独立子进程在运行保存后立即退出时，留下 `CREATED` 记录，但恢复扫描看不到对话登记，重启后没有接续原任务。两个独立应用视图同时提交相同编号时，也会在运行主键处发生重复写入错误。

后续消息已有持久排队，但执行任务、轮次状态和首次审计仍分开保存。在开始处理与取消排队交错时，旧读取可能把已经开始的消息标记为取消，也可能把已取消的消息重新改回处理中；迟到的准备错误还可能将取消状态覆盖为错误。新增测试先在旧实现中复现了这些情况，再进行修正。

## 当前行为

- 首次新建时，任务记录、冻结配置对应的首次审计、对话及首轮登记一起提交。需要清理的原任务草稿也在同一事务处理。任一步失败，整次创建回滚。
- 提交已经保存、页面尚未收到回执时，即使原进程退出，后台仍能找到启动登记并接续同一任务。恢复使用原智能体快照；智能体随后更新或归档不会把已接受任务替换成新配置。
- 相同编号、目标、智能体版本与来源的并发重试返回同一任务。一个编号用于不同内容时返回冲突，不冒充另一个提交的成功回执。
- 重复接收旧任务的回执不会再次删除草稿，保留其他页面后来保存的新草稿。
- 明确待启动的任务继续等待手动开始；每日计划中关闭自动开始的任务也不获得新的自动启动登记。

后续轮次开始处理时，在同一事务确认消息仍然排队，然后保存执行任务、轮次状态及首次审计。取消排队也在写事务中重新检查运行是否已经创建。两个动作按提交顺序决定结果：

| 先提交的动作 | 结果 |
| --- | --- |
| 取消排队 | 消息保留取消状态；准备中的执行事务回滚，不留下运行记录或调用执行器 |
| 开始处理 | 消息保留处理中状态；取消排队返回冲突，页面可使用停止当前轮次 |

准备失败只会将尚未创建运行、仍处于排队的消息标记为错误，不能覆盖其他进程已经取消或开始处理的结果。已保存的运行和排队记录仍使用原有租约与执行轮次保护，避免多个应用视图重复执行同一轮。

## 实现与兼容

2026-10-30 后续补充：新任务与工作流启动在接受事务内核对当前配置，阻止预检之后、提交之前发生的更新或归档竞态；已接受请求仍优先返回原回执。见 [任务接受时的配置一致性](task-acceptance.md)。

2026-10-30 后续补充：草稿清理现要求 `draft_revision`，放弃后保留递增版本；任务回执新增 `task_draft`。过期清理不会影响任务创建，也不会覆盖其他页面的新草稿。具体协议及使用方式见 [多页面任务草稿保护](task-drafts.md)。下文描述提交事务改造时的兼容范围。

没有新增数据表或修改现有任务请求字段。`Runtime.submit` 与 `Store.create` 增加内部 `on_created` 回调，用当前创建事务的连接保存关联控制记录；回调失败时回滚，提交后再通知执行器。Web 首次运行配置、智能体选择及模型发送许可的审计一起保存，不再依靠提交后的临时租约补写。

首次检查点版本从创建版本开始递增，版本仍用于单调更新与租约防护，不依赖固定的初始数值。历史记录保留原值。原有未登记任务仍可通过相同提交编号重试或手动开始；自动恢复只处理明确保存了启动登记的任务，避免将历史待启动任务批量执行。

停止请求的处理保持独立：待处理停止优先进入收尾，不能被普通自动恢复覆盖，见 [任务停止的持久请求与恢复](cancellation.md)。每日计划的持久派发与冻结目标规则见 [每日任务恢复](../operations/daily-recovery.md)。
