# 失败轮次的重试与关联

2026-11-03。当前源码改进，版本仍为 1.3.0，尚未发布。

此前“重试这一轮”把原要求当作普通新消息发送，每次生成新的提交编号。请求仍在进行时可以阻止重复点击，但回执返回后原失败轮次仍显示重试按钮，多个页面也没有共同的重试身份。用户可能生成多个相同轮次，且无法从原失败记录辨认重试结果。

## 使用行为

失败、超时或尚未建立执行记录便报错的轮次可以重试。服务端从原轮次读取完整要求，在同一任务末尾创建一个新轮次；保留原失败状态、错误和生成片段。执行器中断仍使用“恢复原任务”，等待授权或人工核对的操作仍遵守原有规则。

每个失败轮次最多关联一个重试。重复点击、多个页面同时请求、回执丢失后重试和服务重启后重放，均返回同一关联。原按钮变为“已重试 · 查看第 N 轮”，新轮次标明来源，可双向定位。重试再次失败时，从新的失败轮次发起下一次重试，形成可追溯的接续关系。

输入框草稿与重试要求分开保留，即使文字相同，重试受理也不会清空草稿。回执不确定时，原轮次和要求保存在当前标签页；刷新不会自动发送，用户可只读核对，再明确返回对话或重试。后续编辑不会替换原要求。

尚未受理的重试仍检查已查看的对话版本。另一页面先发送新消息时，旧重试会被拒绝；核对后可按当前对话重新提交原轮次。已受理的重试则返回原回执，不因版本变化创建新的轮次。新重试继续使用当前对话历史、原任务冻结的智能体配置和每轮预算规则，并非回滚到旧轮次时刻。

取消排队会保留重试关联，后续重复请求不会复活已取消轮次。需要改变要求时，可在继续对话输入框另发消息。完整对话的 JSON 与 Markdown 导出均保留重试来源和对应轮次，包括已取消的排队重试。

## 实现边界

`POST /api/tasks/{task}/messages/{number}/retry` 只接受 `revision`，不接受替换要求。`GET` 同一路径返回该轮重试的持久回执与当前对话，查不到时返回 404；读取不登记对话、不派发任务。

服务端使用内部 `retry:{number}` 提交身份，复用现有按租户、任务和提交身份的唯一约束，无需数据库结构迁移。普通消息提交编号不允许冒号，不能占用此内部身份。首次接受时在同一写事务内检查来源轮次的当前状态、工作空间、回复许可和对话版本，再保存新轮次、版本与审计。访问继续核对任务所属工作空间和执行身份。

对话投影增加 `retry_of` 与 `retried_by`，来源与结果均来自已保存的请求身份。旧的普通消息保持原语义；本次改进之前通过普通消息入口产生的重试无法可靠识别，不补造关联。

## 验证

新增后端覆盖并发接受、重复回执、取消与重启、来源状态变化、版本冲突、失败链、非法参数、身份与工作空间隔离、HTTP 和完整对话导出。新增前端覆盖固定重试入口、回执丢失后的刷新恢复、按新版本重试原轮次、草稿保护，以及已有重试的定位入口。

真实隔离浏览器通过合成模型产生初始失败和重试失败，验证两页面同时重试只有一次模型接续，再从第二轮重试成功；刷新保留全部原记录与未发送草稿。另验证已提交后丢失回复、提交前断网，以及核对后遇到其他页面更新。现有消息恢复、模型失败提示和执行器恢复验收继续通过。

重试入口在深浅色、1024 / 1440 像素宽度与正常 / 两倍文字共八组桌面布局下可见且可聚焦，重绘保持焦点。已目视核对重试链截图。测试使用临时数据库和合成模型，不调用真实模型服务或业务工具。

测试数量、原始日志、首次夹具修正和候选包摘要见 [验收记录](turn-retries-verification-20261103.json)。候选包按当前程序文件逐项比对源码、独立 wheel 和包内 wheel，并核对包内外 SHA256。本轮未发布，未重复全新环境安装。
