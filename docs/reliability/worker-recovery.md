# 执行器中断的持久诊断与显式恢复

2026-10-29。当前源码改进。此前执行器异常仅留在进程内的 `jobs` 字典中，重启后无法查看原因；对话收尾还可能立即重新派发同一失败轮次，反复消耗资源。

隔离复现中，同一对话在前三次意外异常后自动继续执行，最终只留下完成状态，没有中断事件。另一复现中，重启后错误信息消失。现在将已捕获的中断写入运行状态及审计，后台等待用户明确恢复。

## 使用

- 任务对话显示“执行中断”，保留输入、公开进度和已收到的输出片段。片段仍注明本轮未完成，不当作完整结果。
- 执行进程释放占用后，可“恢复原任务”或“停止本轮”。恢复沿用原任务与轮次、冻结配置、剩余预算和原授权，不复制任务，不重置截止时间。
- 后续补充可以排队保存，但不会使中断轮次自动重试。恢复或停止原轮次后，按原有顺序处理已排队消息。
- 刷新或重启后仍能查看中断原因。任务列表归类为“中断待恢复”，纳入等待处理计数与恢复待办，运行检查页也展示持久诊断。
- 对话 JSON 和 Markdown 导出保留中断原因；Markdown 导出包含已保存的未完成片段及明确标注。
- 模型返回失败或预算已耗尽，仍使用原有终态处理及新轮次重试。执行器中断使用原任务恢复，两个动作不混用。

运行仍有未释放的租约时，界面等待后再开放恢复。写后中断继续使用业务幂等核对；恢复不会重复创建已存在的草稿。若原预算已经过期，恢复仍会按原截止时间结束为超时。

2026-10-30 补充：停止本轮现先保存独立的持久请求，跨进程、刷新和重启后继续收尾；停止处理失败等待“重试停止”。待处理停止不能被普通恢复或新授权覆盖。详见 [任务停止的持久请求与恢复](cancellation.md)。

## 持久化与执行轮次

不新增数据库表。在运行控制状态中保存 `interruption`，同一事务增加版本并写入 `worker.interrupted` 审计事件。任务契约、冻结快照与业务动作保持原值。

```json
{
  "kind": "ERROR",
  "code": "worker_exception",
  "message": "执行进程意外退出，输入与已保存内容保留，请检查后恢复原任务。",
  "exception_type": "RuntimeError",
  "epoch": 3,
  "at": 1793260800
}
```

分类包括执行器拒绝入队、运行时初始化失败、执行过程中意外异常、执行租约丢失，以及已有的写后中断演示。公开诊断保存安全说明和异常类型，不保存原始异常参数、认证材料或调用栈。

每次接受执行请求时，先在事务内推进执行轮次，再提交进程内队列；实际接管运行时核对预期轮次。已被后续请求取代的排队执行器不能接管任务；旧执行器晚到的错误也不能覆盖新尝试。中断的重复登记不会重复写入审计。

手动恢复在同一事务清除当前中断标记并记录恢复请求。新的执行器若再次拒绝入队，会保存本次新错误。CLI 直接恢复同样保留原任务，并记录恢复事件；旧 Web 进程的错误不能覆盖 CLI 恢复后的结果。

对话摘要按轻量字段读取持久诊断，不重新加载全部正文、动作与审计。列表与对话的“中断”是展示状态，内核仍保留实际执行阶段，以便恢复核对。

## 与后台恢复协作

- 对话收尾仅在正常退出时考虑下一轮；后台扫描和实际提交都检查中断标记，避免检查与提交之间的竞态。
- 每日派发重启后先检查任务的持久中断，而不是只检查本进程的 `jobs`。遇到中断后计划显示失败原因，等待“重试原计划”。
- 工作流遇到中断节点时停在 `INTERRUPTED`，不执行依赖节点。新的显式恢复请求可以继续原节点；普通后台恢复不会擅自清除节点中断。
- 数据备份和恢复直接保留中断标记及审计，恢复后的后台也不会自动重试已暂停任务。

本次处理已被程序捕获的异常。若操作系统直接结束进程、程序没有机会记录错误，继续依靠已有运行租约与持久检查点恢复，不能凭空报告具体退出原因。

## 异步界面回执

消息提交、取消排队、恢复与停止都按当前任务范围、对话版本和更新时间接收回执。较晚返回的旧回执不能把已取消消息改回排队，也不能覆盖新状态或已经切换到的其他任务。恢复中的刷新与实时推送继续保留输入、光标和阅读位置。
