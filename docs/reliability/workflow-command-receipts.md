# 工作流操作回执顺序与取消优先级

2026-10-30，当前源码改进。上一轮保护了工作流旧读取，本轮处理已经成功的操作回执乱序，以及取消后的新增授权。

复现中，授权已经接受但响应被延迟；随后取消成功，较早的授权回执仍能把页面恢复为授权排队。另一项服务端复现发现，取消标记已经保存时再次授权仍会写入权限，并把取消派发改成授权派发。执行器仍会检查取消标记，但接口与页面应当一起尊重已提交的停止意图。

## 操作结果保持先后顺序

工作流运行增加只读的 `revision` 字段，由该运行已提交审计事件的最大序号产生。状态正文、取消标记与事件序号在同一条 SQL 中读取；版本号不写回运行正文，不参与冻结配置摘要，无需迁移旧库。没有事件的历史运行返回 0。

| 字段 | 含义 |
| --- | --- |
| 工作流定义的 `revision` | 可编辑流程配置的版本 |
| 运行的 `revision` | 该运行已提交审计的序号，用于比较回执 |
| 运行的 `snapshot.revision` | 创建此运行时冻结的流程配置版本 |

页面按记录 ID 比较已知目录和详情中的版本。较低版本的保存、归档、授权、恢复或启动回执不替换新状态，也不覆盖新提示。取消标记不被旧回执清除，已结束的运行不退回活动状态。版本相同的回执仍可更新执行器与节点进度，避免冻结没有新增流程审计的动态信息。不同运行之间不比较序号大小。

这是运行状态与操作回执的顺序依据，不把多个 HTTP 接口、子任务状态或进程内执行器信息声称为同一数据库快照。旧刷新范围保护继续生效，详见 [刷新与操作回执的一致性](workflow-view-consistency.md)。

## 取消后的授权与重试

- 授权提交事务再次检查持久取消标记。取消在授权预检之后发生时，授权写入及其审计一起回滚，不新增权限，不替换取消队列。
- 取消后发起授权，接口返回 409，并明确说明不能新增授权。
- 取消处理中的提案区域显示“取消请求已保存”和“授权已停用”。即使取消派发失败、执行器不忙，也不能再次授权。
- 取消派发失败提供“重试取消”。恢复请求继续原取消意图和原期限；对旧版本留下的“已有取消标记、派发原因却为授权”的记录，重试会修正为取消。

已经接受的早期授权仍保留原有审计，取消不会撤销已经发生的写入；执行器继续沿用原有停止、回读核对和结果保留规则。浏览器验收的早期授权尚在队列中，随后取消，释放队列后原节点结束且没有创建草稿。

## 异步验收修正

检查浏览器失败时发现，本地浏览器工具的 DOM 轮询把 Promise 当作条件已满足，异步函数解析为 false 后没有再次轮询。之前的一项取消完成检查因此可能过早继续；其他脚本中的同类用法也存在误报或不稳定的风险。

新增共享的 API 等待工具，每次明确 `await` 实际条件；false 继续检查，超时或读取错误明确失败。已替换七个脚本中的九处异步 DOM 轮询。五项回归检查覆盖异步 false、未完成 Promise、超时、读取异常与成功返回值。普通任务验收也更新为当前的“核对提交结果 → 沿用原编号重试”，并检查重试参数与原提交完全相同。

这次重新验证了工作流取消的实际终态，以及任务、对话和每日计划的实际状态。较早记录中相关取消完成检查的依据，以本轮明确等待后的结果为准。
