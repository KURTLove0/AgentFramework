# 四模块知识库与 Agent 工作流

2026-10-22。本次将知识库整理为“知识、记忆、经验、能力”四个可操作模块，并增加由 Agent 节点组成、可通过对话设计的持久化工作流。仍限定为本机 test 工作台与模拟业务工具。

2026-10-31 源码增量：编辑器支持保存回执核对、保留后续修改、复用已创建的专用智能体与明确另存；归档流程及并发更新在写入时受到保护。行为、测试和当前窗口草稿限制见 [工作流保存回执与编辑恢复](../reliability/workflow-saves.md)。

同日后续增量：工作流编辑支持当前标签页的刷新恢复与“保留草稿并关闭”。原提交编号和后续输入分别恢复，目录提供明确的继续入口；边界与验收见 [工作流草稿的标签页恢复](../reliability/workflow-drafts.md)。

启动恢复增量：运行前重新读取配置，未确认结果的启动在当前标签页保留原编号与后续参数。只读核对不重新派发，明确重试沿用原请求，服务重启或流程更新、归档后仍可找到已经受理的原运行。见 [工作流启动核对与恢复](../reliability/workflow-starts.md)。

提案授权增量：授权提交绑定已显示的提案和当前子任务轮次；变化时先核对再审查。授权、持久回执与派发登记一起提交，相同回执重试不续期或覆盖取消。接口现在要求详情返回的 `proposal_token`，详见 [工作流提案授权与核对](../reliability/workflow-grants.md)。

## 使用入口

```bash
python3 -m agent_framework serve --port 8787
```

- [知识库](http://127.0.0.1:8787/#/library)：切换当前业务空间，再进入四个模块。
- [工作流](http://127.0.0.1:8787/#/workflows)：创建节点，或使用“对话创建”。当前空间须有已定义的可用 Agent。

## 知识—记忆—经验—能力

| 模块 | 可操作功能 | 与执行闭环的关系 |
| --- | --- | --- |
| 知识 | 搜索/状态筛选，新增，编辑为新版本，来源/有效期/可见范围，审核、发布、撤回，版本与生命周期审计 | 仅已发布且有效的版本供 Agent 检索；修订不重写已发布正文；关键来源失效停止认知/写入 |
| 记忆 | 本人偏好新增/修订/审核发布，情节检索、原始任务与证据查看 | 偏好只影响受限呈现；终态事实由检查点事务归档，工作流节点与普通任务使用同一记忆链 |
| 经验 | 候选查看，隔离回放与反例评测，查看评测记录，明确审核发布，撤回 | 候选不可进入认知；已发布经验可被后续同主体任务召回，不改变授权与验收 |
| 能力 | 六项能力契约、READ/WRITE 效果与阶段、Tool/CLI/MCP 适配器、幂等与核对规则、当前空间使用岗位、Skill 方法和配置入口 | 可执行能力只能来自受信登记；通过 Agent 编辑器绑定，不能把普通知识文本变成执行权限 |

知识库检索包含可管理的草稿与历史版本；执行时的检索仍使用原有发布/有效期/范围/摘要校验。记忆、经验及对话按主体隔离，资料和使用岗位按工作空间隔离。情节保留原始事实，不提供任意改写事实的接口。

## 对话设计与审查

在“工作流 → 对话创建”中选择当前空间的 Agent。对话使用该 Agent 的身份、Prompt、运行时和模型；模型仅接收流程需求、历史对话、当前提案、空间内可用 Agent 摘要与封闭 Schema。不会启动该 Agent 的业务或原生 MCP 工具。

真实 Codex/Cursor 运行时生成结构化提案或澄清问题。模拟运行时提供明确标注的离线语法：按 Agent 名称、“先…再…”或“并行”组织节点，支持“名称改为…”和“倒序”。自由语言设计应选择真实 CLI Agent；离线语法不伪装为真实模型推理。

例如，空间中已有“交易知识助手”和“交易变更审核员”时：

> 先让交易知识助手查询风险与草稿验收规范，再让交易变更审核员评估模拟变更并创建草稿。

可以继续对话修改提案。历史设计对话保存在同空间、同主体范围内，关闭页面后可继续查看。提案经“审查并编辑”进入节点表单；保存、运行和写入授权分别进行。对话 Schema 没有权限、命令或故障注入字段，生成提案不会自动执行。

缺少合适的执行者时，设计智能体还可自主提出专用智能体草案；画布内可审查和修改，保存流程时一起创建并绑定为实际执行节点。空空间也可直接从画布创建执行智能体。详见 [流程内创建执行智能体](../workflow-agents/implementation.md)。

## Agent 节点与执行

每个节点指定 ID、名称、Agent ID 与 revision、目标、依赖节点。保存时检查 Agent 是否可编译、版本是否当前、依赖是否存在、有无循环。支持 1–12 个节点的 DAG，包括多支依赖和汇合；当前调度器按确定顺序执行就绪节点。

开始运行时冻结工作流定义、全部 Agent 配置和编译结果。后续编辑或归档不会重写已有运行。节点通过原 `Runtime` 创建 Agent 任务；上游成功并经独立验收复核后，其完整产物连同来源运行 ID、节点 ID 和摘要进入下游 `TaskContract.workflow_inputs`。该数据不授予权限，不替代下游领域的可信工具证据。

运行记录展示每个节点状态、必选检查通过数、草稿数量及原任务链接，并可查看冻结输入、流程摘要和审计事件。流程编辑只影响后续运行，可归档/恢复使用。

## 授权、失败与恢复

- 未授权的写节点停在具体提案，展示项目、变更、参数和摘要；明确授权该提案后继续。依赖节点不会越过未通过验收的上游。
- 真实节点须确认模拟上下文发送许可；原生 MCP 须单独许可且限已登记读取代理。
- 提交运行的 `request_id` 对同一主体/空间幂等。相同 ID 重试返回原运行，不同参数重用被拒绝。
- 每个节点使用由工作流运行 ID 与节点 ID 派生的固定子任务 ID。先持久化节点意图，之后创建子任务；即使创建后、流程检查点前中断，也会恢复同一个子任务。
- 编排器与子任务各有持久化租约。工作流检查点校验编排器持有权；原 Runtime 负责动作持久化、当前授权、未知写入核对与幂等恢复。
- 恢复前检查节点链接、Agent 编译摘要、任务目标、范围及冻结输入绑定；已完成上游的当前来源再次失效时，先停止并核对已派发的在途写入，再转人工核对，不继续派发下游。
- WAITING_AUTH、WAITING_INPUT、PAUSED、INTERRUPTED 可恢复同一流程；失败/人工核对等终态不会自动重新创建写入。
- 服务会检查已接受但未完成的运行，并接续 CREATED/RUNNING 状态；节点补充回答全部处理完成后，遗漏的续跑通知也可恢复。此检查按当前用户覆盖全部可用空间，不受界面最近 100 条记录限制；授权等待、手动暂停和故障中断仍通过原入口处理。见 [恢复机制与验证](../reliability/implementation.md)。
- 启动、授权、恢复与取消均保存待执行请求。执行队列已满时接口返回已接受，并在列表和详情显示排队；授权和续跑请求在同一个事务保存，服务重启后也能接续。排队不延长授权有效期；执行器异常保留明确的重试入口。
- 取消在当前动作返回后核对结果，保留既有草稿与审计；不确定效果保留人工核对状态。默认流程期限 1800 秒，节点期限不超过剩余期限及 600 秒，冻结上游输入总大小限制为 48 KB。
- 存在未完成工作流的空间不能删除。每个写节点独立拥有草稿身份；恢复不会重复创建该节点的草稿。

工作流页面会保留最新操作回执，晚到的旧目录或详情不能覆盖保存、归档、授权与取消结果；切换运行或页面后，过期读取也不能替换当前详情或错误说明。详见 [刷新与操作回执的一致性](../reliability/workflow-view-consistency.md)。

## 可复现实验

```bash
# 知识库→两轮对话→审查保存→节点授权→丢回执→重启恢复，独立模拟目录
python3 -m agent_framework.workflow_evaluate

# 同一演示，再调用一次本机 Codex，生成真实结构化流程提案
# 仅使用程序固定生成的模拟岗位和需求；模型 ID 应存在于本机 CLI 目录
python3 -m agent_framework.workflow_evaluate --live-codex --model gpt-6.1-sol

# 全部回归与原 44 个故障用例
python3 -m unittest discover -s tests -q
python3 -m agent_framework.p0_evaluate
```

验证记录：**163 项自动测试通过、44/44 原故障用例通过、7/7 独立演示用例通过**。真实 Codex 提案使用 `gpt-6.1-sol`，1 次调用约 17.27 秒，输入 17216、输出 341 tokens；无 MCP 调用。真实模型提案又在独立工作台中审查、保存、运行，两项 Agent 节点均验收 3/3；执行节点采用模拟认知及业务工具，知识节点零草稿、评估节点一份草稿。

主工作台已演示知识 v1→v2 审核发布、检索、能力使用岗位、节点记忆归档、经验隔离评测发布，以及工作流等待授权、写入回执丢失和服务进程重启恢复。中断恢复保留原流程摘要、原子任务 ID/快照、原写入参数，创建调用仍为一次。原有 28 个任务快照与操作前记录的摘要相同。

详细运行 ID、原始回执、源码摘要与要求逐项结果见 [verification.json](verification.json)。

## 接口与存储

| 接口 | 行为 |
| --- | --- |
| `GET /api/knowledge-hub?query=...` | 四模块资料、记忆、经验、能力契约及使用岗位 |
| `GET /api/knowledge/assets/{ref}/history` | 授权范围内的版本与生命周期审计 |
| `GET/POST /api/workflows` | 列表/创建 |
| `GET/POST /api/workflows/{id}` | 查看/编辑（revision 冲突检查） |
| `POST /api/workflows/{id}/archive` | 归档/恢复使用 |
| `POST /api/workflows/{id}/start` | 审查后启动，支持 request_id |
| `GET /api/workflow-starts/{request_id}` | 按原启动编号读取同租户、空间、主体的运行与当前状态，不重新派发 |
| `GET /api/workflow-runs/{id}` | 状态、子任务、待授权提案与事件 |
| `POST /api/workflow-runs/{id}/resume\|cancel\|grant` | 恢复、取消、具体节点提案授权 |
| `GET/POST /api/workflow-chat` | 私有设计对话列表/发消息；发送需 request_id、agent_revision 和布尔 consent，重复提交返回原结果 |
| `GET /api/workflow-chat/{id}` | 继续查看已有对话 |
| `GET /api/workflow-chat-requests/{request_id}` | 私有原请求、处理状态、已保存结果和当前对话，只读核对 |

设计请求新增 `workflow_chat_requests` 表，保存处理权、原参数与回执；对话和结果原子提交。页面恢复、版本检查及备份边界见 [工作流设计请求的核对与恢复](../reliability/workflow-design-recovery.md)。

新增 `workflows`、`workflow_runs`、`workflow_events`、`workflow_chats` 表；后续恢复改进增加 `workflow_dispatches` 保存待执行请求。列表的各运行及详情提供 `queue`（`QUEUED`、`RUNNING`、`ERROR` 或 `null`），附请求类型、提交时间和错误说明。旧任务没有上游输入时，序列化中不添加新字段；旧快照、动作身份、参数摘要及恢复规则保持原值。缺少结构化定义的历史 Agent 仍可按原默认岗位编译并接入新流程；无法编译的配置不会被推荐为可用能力或对话节点。HTTP 沿用 Host/Origin/CSRF 与空间选择检查，流程运行和对话还按主体隔离。

这是本机可运行实现，没有连接真实业务平台；当前模型对话仍限获准的模拟上下文，不宣称生产 IAM、生产发布或任意脚本工作流能力。
